## 第 1 轮问题

**🔴 Q1 · 首批简历来源**
- a（推荐）HR 手工批量上传（Web 工作台拖入 PDF/Word），不接任何渠道——与 §3「渠道对接不在 MVP」一致，合规面最小
- b 汤丽萍经值守通道私信转发简历文件——复用今天已通的通信链路，但把候选人个人信息引入值守归档（章程红线 ⑨ 与留存策略要改）
- c 两者都要

**🔴 Q2 · 真实简历入库前的合规闸**
- a（推荐）先用**脱敏/历史离职候选人**样本做评测集与开发；真实在招简历入库严格等「合规验收 #1」（PIA＋同意条款＋留存策略）通过
- b 评测集也等 PIA 通过后再建（更稳，M2 整体后延）

**🔴 Q3 · 200 份私有评测集谁标、怎么标**
- a（推荐）汤丽萍牵头、按岗位分批（每批 ≤20 份）用「判例批改表」形式标注关键字段（姓名/年限/技能/公司）与人工排序；经跟进信线发、经私信回件归档（依赖 G1 附件链路）
- b 业务经理各自标本部门岗位（口径更准，但协调成本高）
- c 工程侧先用模型预标、人只做校对（快，但「基线」带模型偏差）

**Q4 · 解析字段范围（首期）**
- a（推荐）只做验收要求的四类（姓名/年限/技能/公司）＋ 教育与期望城市，ECU 行业特化字段（§2.4）第二期
- b 首期即覆盖 §2.4 ECU 特化字段

**Q5 · 低置信度处理**
- a（推荐）字段级置信度＜阈值 ⇒ 进人工校对队列，不参与硬门槛判定
- b 整份简历置信度低才进队列

**🔴 Q6 · 硬门槛淘汰的最终决定权**
- a（推荐）硬门槛只「标记不符合＋给出原文依据」，淘汰动作一律 HR 在工作台批量确认；`rejection_record.reason_type=ai_score` 恒为 0（§3 合规验收项）
- b 明确的客观门槛（如学历/证书）可自动淘汰，其余人工

**Q7 · 匹配模型栈**
- a（推荐）按 §3：BGE-M3 召回 → LLM rubric 精排，每条评分带 evidence span；W1 模型对比实测定型（M1 的 `docs/m1-model-comparison.md` 可复用网关与对比脚本）
- b 先只做 LLM rubric 精排（小批量岗位不需要召回），召回第二期

**Q8 · 工作台载体**
- a（推荐）沿用 M1 的 Web（`.51` 门户下 `hr/recruit-agent`），新增「候选人列表／复核／批量确认」页
- b 企微内卡片审批（M1 已把企微回调卡片移出到阶段二，成本高）

**Q9 · 验收门槛是否沿用 §3 原值**
- a（推荐）沿用：解析关键字段 ≥90%、Spearman ≥0.7、Top-10 召回 ≥85%、100% 评分可回溯 span
- b 首期放宽（例如 Spearman ≥0.6），第二期收紧

**Q10 · 首个试运行岗位**
- a（推荐）从 M1 试点的 3 个真实岗位（供应链总监、底层软件工程师、非标产品采购员）里选 1 个在招岗位
- b 另选一个简历量大的岗位（样本足，但 M1 画像要先跑）
