# M2 简历解析与评分排序 · intent（需求收敛结论）

> 来源：`docs/roadmap/M2-需求树草稿.md` 第 1 轮，Shao Peishen 2026-09-17 全部取推荐项。本文件是 `openspec propose` 的输入，逐条可充当 design.md 的 Decisions。依据文档：`02-系统架构与MVP范围.md` §2.1–2.2、§3 M2、§6。

## 目标
HR 上传一批简历 → 解析出结构化字段 → 硬门槛标记（带原文依据）→ 召回＋rubric 精排（每条分带 evidence span）→ HR 在 Web 工作台复核与批量确认。首个试运行岗位取自 M1 试点三岗之一。

## 决策
- **D1 输入（Q1a）**：只做 HR 在 Web 工作台手工批量上传 PDF/Word；⛔ 不接渠道、⛔ 不经值守通道收简历（值守归档保持不含候选人个人信息，章程红线 ⑨ 不变）。
- **D2 合规闸（Q2a）**：开发与评测集只用**脱敏或历史离职候选人**样本；真实在招简历入库受「合规验收 #1」（PIA＋同意条款＋留存策略）机器闸控制——闸未开则上传接口拒收真实简历（开关默认关，开启需人工决定，同 M1 产线开关口径）。
- **D3 评测集（Q3a）**：200 份私有评测集由汤丽萍牵头，按岗位分批（每批 ≤20 份）以「判例批改表」标注关键字段与人工排序；经跟进信线发、经私信附件回件归档（依赖 G1 附件链路 `0917W`）；标注结果导入评测集的格式与校验属本包范围。
- **D4 字段（Q4a）**：首期抽取 姓名/工作年限/技能/公司 ＋ 教育/期望城市；§2.4 ECU 特化字段第二期。
- **D5 低置信度（Q5a）**：字段级置信度低于阈值 ⇒ 该字段进人工校对队列，且不参与硬门槛判定。
- **D6 硬门槛（Q6a）**：只标记「不符合」＋原文依据，淘汰一律 HR 在工作台批量确认；`rejection_record.reason_type='ai_score'` 行数恒为 0（机器断言，进 `COMPLIANCE_ASSERTIONS`）；开放申诉。
- **D7 模型栈（Q7a）**：BGE-M3 召回 → LLM rubric 精排，每条 `criterion_score` 回指 evidence span；开工第 1 个单元是模型对比实测定型（复用 M1 LLM 网关与 `docs/m1-model-comparison.md` 方法）。
- **D8 工作台（Q8a）**：沿用 M1 Web（`.51` 门户 `hr/recruit-agent`），新增 候选人列表／字段校对／复核／批量确认 页；⛔ 不做企微卡片。
- **D9 验收（Q9a）**：解析关键字段准确率 ≥90%；与 HR 人工排序 Spearman ≥0.7；Top-10 召回 ≥85%；100% 评分可回溯 span；`ai_score` 淘汰记录 0。
- **D10 试运行（Q10a）**：从 M1 试点三岗（供应链总监／底层软件工程师／非标产品采购员）选 1 个仍在招的岗位。

## 建议交付单元（propose 时细化）
U0 模型对比定型 → U1 数据模型（ATS 域＋评分审计域 schema）→ U2 上传与解析管线（含置信度与校对队列）→ U3 硬门槛引擎（标记＋依据＋申诉）→ U4 召回＋rubric 精排＋evidence span → U5 工作台页面 → U6 评测集导入与指标脚本 → U7 合规断言与真实简历入库闸。

## 不做
渠道对接、简历爬取、企微卡片、表情/情绪分析、AI 自动淘汰、ECU 特化字段（二期）。

## 不可代项（进 tasks 时标注）
合规验收 #1 的 PIA 与法务结论；`.51` 发版；真实简历入库开关开启；评测集人工标注。
