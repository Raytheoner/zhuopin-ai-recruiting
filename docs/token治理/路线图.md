## 二、路线图总览

排序依据：**确定性高、质量零风险的先做；可能影响交付质量的（换模型）要带 A/B 验证。**

| Phase | 主题 | 预期打哪块 | 质量风险 | 执行 |
|---|---|---|---|---|
| **0** | 建量尺、复核报告数字 | —（基线） | 无 | CC · `[Mac]0916A` |
| **1** | 看护者去轮询：阻塞等待 + 看护者用 Sonnet | 看护会话的轮数与峰值上下文 | 无 | CC 看护件（P0 后出） |
| **2** | 模型分级路由：泳道默认 Sonnet，Opus 按件显式声明 | 无头泳道与子代理的单价 | **有** → 带 A/B | CC |
| **3** | 滚动大文件拆分 + 体积闸 | 开场与改文档时读进来的大块 | 无 | CC |
| **4** | 大回显机器拦截（hook，不靠提示词） | 会话中段的上下文膨胀 | 低 | CC |
| **5** | 启动底座瘦身（按 P0 实测构成下刀） | 每个会话/子代理的首轮 | 低 | CC ＋ 他在 claude.ai 关 skill（如需） |
| **6** | run-build 子代理链路调优 ＋ 账本常态化 | 构建批次；防回潮 | 中 → 带 A/B | CC |

**P0 校正：排序不变。** 实测（`docs/token治理/P0-对账.md`）：看护会话（Phase 1 打击对象）成本占比 7.85%（$60.22/$767.33），高于 5% 门槛，未触发降级；泳道/opener＋子代理（Phase 2 打击对象）合计占比 91.8%，是压倒性大头，维持当前排序（Phase 2 优先级高但因换模型有质量风险，已带 A/B，排序合理）。

## 三、各 Phase 明细

### Phase 0 · 建量尺、复核报告（`[Mac]0916A`）

- **做什么**：跑 `scripts/token_ledger.py`（已写好并用构造数据测过：按 `message.id` 去重、`<synthetic>` 不计费、官方价格折算）统计 09-01～09-15，产出 `docs/token治理/baseline-0901-0915.{md,json}`；把报告 13 条里依赖日志的数字逐条填「实测值 / 报告值 / 是否成立」。
- **重点要量的**：成本按模型与会话类型（看护 / 泳道 / 子代理 / 交互）的分布；单次调用上下文分段；首轮上下文中位数（主会话 vs 子代理）；≥10KB 大回显的来源；被读最多的文件。
- **验收**：基线文件已提交；对账表 13 行每行有实测结论；若数据推翻了下面的排序，当场在本文件「二」改排序并写理由。
- ⚠️ 口径提醒：报告若没按 `message.id` 去重，同一次调用会按内容块重复计数，数字会系统性偏高——P0 的数和报告对不上很正常，以 P0 为准。

### Phase 1 · 看护者去轮询

> 状态（09-16）：`[Mac]0916B` 已出——`docs/openers/wait-lanes.sh` ＋ 两份测试 ＋ `lane-dispatch` skill 盯守节规格。P0 上限提示：看护只占基线成本 8%（$60/$767），本 Phase 省得少但零风险；大头在 Phase 2（泳道 95% 调用是 Opus）。
> 实效验收挂在下一批真实泳道上（与 Phase 2 的 A/B 同批看）。

- **做什么**：
  1. 新建 `docs/openers/wait-lanes.sh`：一次调用在 shell 里**阻塞等待**（最长 9 分钟，低于 Bash 工具 10 分钟上限），直到 `results.tsv` 行数变化、主进程退出或超时才返回，**只打印一行增量**（新完成了哪条、什么状态）。
  2. `lane-dispatch` skill 与看护 opener 模板的「轮询盯守」节改成：循环调 `wait-lanes.sh`，⛔ 不再手工 `cat results.tsv; ls -la *.log`；读失败日志一律 `tail -50`，⛔ 不读全文。
  3. 看护件的【设置】注明模型 Sonnet（看护是判状态、跑固定核验，不是架构推理）。
- **为什么不照报告做纯脚本**：看护者的发车、真身核验、PARTIAL/FAIL 判断和报告仍然需要模型；要砍掉的只是「每 3–5 分钟醒一次」。改完后一个 5 小时的批次，看护轮数从上百降到「状态变化次数＋每 9 分钟一次心跳」，大约 30–40 轮，且每轮只增加一行输出。
- **验收**：下一批看护会话在账本里的调用数与峰值上下文，对比基线里的 `0904Z / 0909AZ` 类会话。

### Phase 4 · 大回显机器拦截

> 状态（09-16）：`[Mac]0916G` 已出。按 P0「大回显 Top 15」只拦能在执行前算出大小的四种读法（`cat`／`sed -n 'A,Bp'`／`head`／`tail`，> 20 KB），hook `scripts/hooks/limit-output.py` 挂 PreToolUse(Bash)，fail-open、管道/重定向/heredoc 放行、`# allow-big-output` 显式放行。榜上的 `Read:task-N-brief.md`（子代理读自己的任务书，属必要读取）与 `Bash:echo` 不拦。HEADER ⑥ 未加（改执行器要等无批次窗口，且 hook 已覆盖）。

- **做什么**：加 PreToolUse(Bash) hook `scripts/hooks/limit-output.py`：
  - `cat` 目标文件 > 20 KB → 拒绝并提示用 `head`/`sed -n`/`grep` 或 Read 分段
  - `pytest` 不带 `-q` → 拒绝并提示 `-q --tb=short`
  - `git log` 不带 `-n`/`-<数字>`/`--oneline ... | head` → 拒绝
  - `git diff` 不带 `--stat` 且不限定路径 → 提示先 `--stat`
  同时把这四条写进 `run-lanes.sh` HEADER 第 ⑥ 条（报告建议里这一条是对的，但光写提示词压不住，所以加 hook）。
- **判据以 P0 为准**：只拦账本「大回显来源 Top 15」里真实出现的命令，不凭想象加规则。
- **验收**：下一批账本大回显次数与 MB 数对比基线；hook 自带单测。

## 五、候选 Phase 7 · 长会话 Workflow 化试点（2026-09-16 追加，待 P0 数据决定是否执行）

**问题**：引入 Claude Code 的 Workflow（脚本编排多个子代理）对长泳道会话省不省 token？

**机制上能省的三处**
1. **编排本身不花 token**：Workflow 脚本是确定性 JS，串行/并行/等待都在脚本里 `await`，不是模型一轮一轮地查。看护者轮询这类开销直接归零（比 Phase 1 的阻塞等待更彻底）。
2. **切断滚雪球**：每个 `agent()` 是全新上下文（带 CLAUDE.md 与工具定义，不带前面的对话）。一个会话的 cache read ≈ 轮数 × 平均上下文，拆成几段后每段从底座重新起步。
   - 按报告里 `0909AJ` 的形状粗算：191 轮、上下文 74k→235k，平均约 155k ⇒ 约 2900 万（与报告的 2880 万吻合）。拆 4 段、每段约 48 轮、每段 74k→约 115k，平均约 95k ⇒ 约 1800 万，**省约 35–40%**。
   - 同一算式也说明：**底座越大，拆分收益越小**（74k 底座每段都要重付），所以 Phase 5 要排在它前面。
3. **自带模型路由与断点续跑**：`agent()` 可按段指定 `model`/`effort`；失败后 `resumeFromRunId` 让已完成段直接复用结果，不像 `--chain` 重跑那样白花。结构化输出（schema）代替哨兵解析，只把几行结论交回主会话。

**不省甚至更费的情况**
- **切得太碎**：每个子代理都重付一次底座，几轮就完的小段反而贵。切分粒度＝一个自然交付单元（一个 plan Task、一个发版步骤），不是一条命令。
- **不可拆的调试线**：像 TD-39 重连链这种要靠前面积累的线索往下查的，拆开后下一段要重新读日志、重新定位，可能更贵、质量也更差。
- **不指定模型时子代理继承主会话模型**：主会话是 Opus 就全是 Opus——和 `run-lanes.sh` 的 `MODEL=""` 是同一个坑，每段必须显式写模型。
- **加验证模式**（多票复核、裁判团）是花 token 买质量，要按需开，不能默认。

**和本项目机制的冲突点（试点前必须先验证）**
- Workflow 跟随发起它的 session 存活，断点续跑只在同一 session 内有效；`run-lanes.sh` 经 launchd 起、独立于任何会话。Mac 休眠 / Desktop 关闭时 Workflow 能否撑过，要实测。
- 脚本里没有文件系统和时钟，不能自己查 `results.tsv`、`ps`；但若泳道本身就是 `agent()`，也就没有东西需要查。
- 🟡/🔴 门禁不能在运行中等人：到门禁即返回，下一段另起一个 Workflow。
- 并行段在同一检出上改文件仍要守并发协议，或用 `isolation: 'worktree'`。
- 他的 CC 版本（Desktop 与 `claude -p`）里是否有 Workflow 工具，要先查。

**试点做法（若执行）**：只选一件「P0 账本里成本 Top 10、且标为可切分」的长会话类型，改写成 3–5 段 Workflow，每段显式 Sonnet（设计段除外），与基线同类会话对比成本和结果质量。`run-lanes.sh` 在试点证明之前不动。

**排序**：P0 → P1 → P2 → P5 → **P7 试点** → P3/P4/P6 视数据。
