## 四、未达标项与回归方向

**指标 3：单次调用上下文 ≥150k 占比，实际 15.7%（仅无头泳道口径），差达标线 6.4 个百分点。**

定位到具体会话（仅无头泳道口径下，≥150k 次调用数 Top）：

| 会话 | 类型 | ≥150k 调用次数 | 峰值上下文 | 总调用 |
|---|---|---:|---:|---:|
| `[Mac]0910G-P0回件桥实现计划` | spec-to-plan | 73 | 321777 | 116 |
| `[Mac]0916P-P0建造Task7至9` | run-build（波次 2） | 52 | 239755 | 99 |
| `[Mac]0916U-P2建造Task4至5` | run-build（波次 2） | 39 | 191454 | 105 |
| `agent-a0`（子代理） | 子代理 | 31 | 186834 | 58 |
| `[Mac]0916V-P3建造Task1至4` | run-build（波次 2） | 28 | 202509 | 93 |
| `[Mac]0916E-TD29收尾liaison测试脚手架收编与config文案` | run-build | 25 | 167124 | 81 |
| `[Mac]0910H-P1打标即开班实现计划` | spec-to-plan | 25 | 212885 | 56 |
| `[Mac]0910J-P3口径点台账实现计划` | spec-to-plan | 20 | 181859 | 62 |

**原因**：这 8 条会话贡献了 293 次 ≥150k 调用里的 293 次（全部）。共同特征是**单会话内连续多轮**（56～116 次调用）持续在一次对话里推进——spec-to-plan 三条是长篇设计推理（读 spec/design 多个文件并反复引用），run-build 三条是波次 2 的建造段（`0916P/U/V`，每条覆盖 3 个 Task）。

已落地的两道机制都只**部分覆盖**这个模式：
- Phase 6（`e21d90f`）的 `context-guard.py` 在 150k/250k 提醒模型"换任务先换 session"，是**提示词层面的提醒，不是强制中断**——spec-to-plan 类会话本身就是一个不可拆的连续设计任务，提醒后模型仍需要在同一会话内做完。
- Phase 7·A 路（`d064744`／`c491230`）的拆段规则只对 **run-build 且 plan ≥5 Task** 生效，`0916P/U/V` 已经是拆过的波次 2（每条 ≤3 Task），仍然各自跑到 93～105 次调用——说明按 Task 数拆分并不必然把单条控制在低上下文区间，因为每个 Task 内部的实现＋两阶段 review 本身就会滚雪球。spec-to-plan（`0910G/H/J`）目前不在任何拆分规则覆盖范围内。

**回归方向**：不回退 Phase 2/3/4/5（已达标，无副作用），把此项计入 **Phase 6/7 的下一轮深化**：
1. Phase 7：评估把拆分粒度从「按 Task 数」改为「按累计上下文阈值」（例如单条估算峰值 ＞180k 时提前收段），而不只是 Task 计数。
2. Phase 6：spec-to-plan 类长设计会话是否需要单独的拆分策略（目前的护栏假设"换任务"，但设计推理任务往往就是一个任务、拆不开）——需要先画像这类会话的调用形状再决定是否投入。
3. 两项都建议先在下一批同类会话上小样本验证，不整体改规则。

## 五、局限

- 治理后样本仅约 1 天（2026-09-16 至今），且以「Token 治理工作本身」（10 条手工会话）与「run-build/spec-to-plan 建造」为主，工作构成与 09-01～09-15 基线期（更多 intake/web/审计等特性开发）不同，不是严格同构对比。
- 账本口径只覆盖本机 `~/.claude/projects` 下的 Claude Code 会话日志，**不含 Cowork 会话成本**（Cowork 侧看护、需求/文档工作的 token 消耗不在此账本内）。
- 指标 2（看护）判定为"机制替代"，是因为无头泳道口径下真实看护会话数为 0（已改由 Cowork 远程看护），并非本机机制把看护成本压到了 0——该项后续应换成对 Cowork 侧看护会话的独立核算，而非默认满足。
