# kickoff skill 由来与实证

本文件收纳 `.claude/skills/kickoff/SKILL.md` 里「为什么／根因／血的教训／历史归因」性质的段落——
读一次就够，不是每次出 opener 都要重读的判据。**判据、模板、禁令本身留在正文**，
正文对应位置留一行指针指回这里。拆分动作见 `docs/openers/0920E-kickoff瘦身拆由来.md`。

---

## MMDD 必须实跑的原因

> *为什么必须实跑*：开发机在美东（EDT），**比中国时间晚 12 小时**——本机的晚上就是中国的次日中午。
> 照本机日期编号，跨过那条线之后出的 opener 会集体落在"昨天"，而**编号错了不报错**，
> 只在日后跨会话对账时对不上。实证：2026-08-27（中国时间）出的一批全被编成了 `0826-*`，
> 是 Shao Peishen 问「这个是否改成 0827 更合适」才发现的。
> ⚠️ 这条不适合做成 hook 机器拦——重发历史 opener 时编号本就该保持不变（见下方「重发」一节），
> 拦了会误伤。所以它只能靠**出 opener 前实跑一次命令**这个动作来保证。

## id 用 `-` 分隔而非空格的原因

> *为什么弃用空格*：主题短名常以 ASCII 开头（`audit U1计划`、`.51整机重启`），
> `[Mac] 0826-D audit U1计划` 肉眼一扫读不出 id 在哪儿结束。`-` 唯一且紧凑，无歧义。
> 主题里再出现 `-` 不影响解析——判据是**第一个** `-`。

## `[Mac]` 前缀值得占用字符的原因

> *为什么值得占这几个字符*：Win 笔记本与 Mac 两台都在跑。启用 Remote Control
> （从 claude.ai / App 控制 Claude Code）后，那一侧列出的是**跨机器**的 session，
> 没有这个前缀就分不清哪条在哪台上。⚠️ 它标的是机器不是界面——
> ⛔ 不要写成 `[CC]`：Code tab 下条条都是 CC，零分辨力。

## 派发字段不能留空的原因（0908J 实证）

> *为什么*：他在 Desktop 同时开多个 session，拿到一份 opener 却**回溯不到是谁派的**。
> 出问题时要回母 session 看派发上下文——`[Mac]0908J` 实例：opener §三 预告的
> 「断言四会翻成违例」在执行时已过时（`0904F` 改了豁免线），执行方要判断这是"漏跑"
> 还是"前提已变"，就得回母 session 看它写这段时依据的是什么。查不到就只能猜，
> 而这两种情况的处置**完全相反**。
> ⚠️ 落了档的 opener 还能靠 `git log --diff-filter=A -- docs/openers/<件>.md` 反查
> （`0908J` 即由此查出母 session 是 `[Mac]0908B`），但**聊天里直接派、没落档的查不到**——
> 字段要解决的正是这一类。

## 号池撞号实证（08-27 一天撞 4 次）

*实证*：08-27 `0827E` 被派给三个不同 session（提交 session 命名根治／提交 opener 补丁／
提交命名实测与自检），`0827D` 撞两次。根因不是记性——是**提交类、清理类这些一次性
opener 只出现在聊天记录里，从不落档** ⇒ 下一轮 grep 只看得到编排文件里那几个
（`A/B/C/Z`）⇒ 每轮都判定 `D/E` 是空号 ⇒ 必然重派。

## 标题行漏写的实证与归因更正（2026-08-26／08-27）

*实证*：2026-08-26 发现左侧会话列表里近期会话**全部丢失编号**，而更早的 `【OP-0820-*】` 一批都有。原因是某条会话连续给出八份中途指令，全部用了 `界面／Session／分支／Worktree` 四行式、一份都没带标题行。

> ⚠️ **当时对这条实证的归因是错的**（2026-08-27 更正）：以为「侧边栏拿不到标题行就用首句猜」，
> 实际侧边栏根本不看首行，用的是 Haiku 摘要——详见下一节。
> **但这条实证本身仍然成立**，只是它证明的是另一件事：缺头两行时，**被复制进去的那个
> session 自己不知道跑在哪、该不该勾 worktree**，这才是头两行的真正用途。
> 编号的可 grep 性另由「会话命名」那节的两条路保证。

## 两条被实测推翻的假说

🔴 **两条被实测推翻的假说，别再提出来**：

1. ~~「标题行以 `[…]` 开头就会被沿用」~~ —— **不会**。不显式设置就是 Haiku 读首条消息
   现写摘要，与首行无关。
2. ~~「长度超限会吃掉编号」~~ —— **32 字符的标题实测完整保留**
   （`[Win] 0827-A 波次收口-解master分叉与四分支合入`）。那边为这个假说立过三条规则，
   提出后 2 分钟被实测推翻。

📌 **那边最值得抄的不是格式，是这条判据**：**一个假说在写成规则之前，先问「有没有一个
5 分钟就能做的实验能推翻它」。** 本例中那个实验就是「设一个长标题看会不会被截」，
成本几乎为零，而两边都没做就先写了规则。

## Cowork 首行走摘要的实测细节

开场词首行写 `HR业务线-接力0827B`，侧边栏显示 **`HR业务线接力`**。
既不是原样，也不是截断（截断会留 `HR业务线-接力`）——**连字符和编号一起被改写掉了**，
这是摘要改写的特征。同屏其他条目也印证：`Human Resource documentation updates`
这类英文名不可能来自中文首行。

## 重发铁律的由来

*为什么*：聊天里 opener 总是被孤立复制的——收到一个无头代码块，人得往回翻十几屏找"这块是哪个任务"，找错就跑错环境。实证来自企业AI转型的真实反馈：「虽然我可以推断，第一张图是哪个任务的 Opener 不明晰」。

## 两条抬头规则的完整展开（2026-09-09 从 CLAUDE.md 移出）

移出原因：CLAUDE.md 触了防膨胀关三（全文 252 > 250 行、「强制格式」节 41 > 40 行）。
正文留的是**判据本身**，这里留**判据的由来、实证与豁免**。⛔ 两处冲突时以 CLAUDE.md 为准。

**`set_session_title` 为什么必须是第 3 行**：标题行**不会**自动变成 session 名——不调这个
工具，侧边栏就丢编号，他同时开多个 session 时分不清哪个是哪个，`set_session_title` 那条
规则的全部价值当场归零（与撞号的代价相同）。照抄这句：

```
开工第一件事：调 mcp__ccd_session_mgmt__set_session_title（session_id 传字面量 "self"），标题：[Mac]MMDDX-<主题短名>
```

- **Cowork 侧首行无效**（走摘要，2026-08-27 实测）。⛔ 不要再改首行格式硬试，那条路已经试过了
- **唯一豁免**＝`run-lanes.sh` 无头起的块
- 机器判据见 `scripts/hooks/check-opener-header.py`；旧格式 `【OP-…】` 仍放行、不追改

**`派发` 为什么不能留空**：他在 Desktop 同时开多个 session，收到一份 opener 却回溯不到是
谁派的——出问题要回母 session 看派发上下文时只能靠猜。四种取值，⛔ 不留空、不写"未知"：

| 情形 | 写什么 |
|---|---|
| 母 session 有编号 | 该编号，如 `[Mac]0908B` |
| Cowork 派的 | 会话名，如 `Cowork·HR业务线-接力0903B` |
| 他本人口述、无母 session | `Shao Peishen 口述` |
| `run-lanes.sh` 无头起 | `run-lanes.sh` |

机器判据见 `scripts/hooks/check-opener-header.py` 判据③。

## 并发四条内嵌的由来

*为什么*：并行跑两条线改同一个文件，冲突不会在写的时候报错，会在提交时才发现，而那时两边的改动都已经写完了。事前列触碰区 + 内嵌自愈四条，是唯一便宜的防法。

## add 清单实证（0909AH／TD-39）

*实证*：`[Mac]0909AH`（TD-39）的【提交】只列了 `session_client.py`、`tests/`、`docs/tech-debt.md`
和 opener 自己，**漏了 `tools/liaison/__main__.py`**——而看门狗必须在 `main()` 里起线程才有用。
守着清单不改，交付的就是一段**没人调用的死代码**，而 opener 的目标（N-0 兜底）等于没做，
且⛔ **不会有任何症状**：单测全绿、TD 落档写着"已修"，只有真实断线时才发现兜底层是空的。

## 一键复制铁律的由来

*为什么*：手工拼接是纯粹的出错来源，且错了往往不报错——比如漏掉 Global Constraints 修正，后面每轮 review 都是瞎的，但过程看起来一切正常。

## 判据禁止漂移——0910B 反例与同族旧教训

⛔ 反例（`0910B` 真踩过）：「`git log --oneline -3` 应能看到那条 commit，看不到 ⇒ 停下报『前提还没上 main』」。
opener 写成时那条 commit 排第 1，几小时后被别的 docs commit 挤到第 12 ⇒ 判据**假阴性**，
而它输出的结论是**反的**（前提其实一直成立），执行者按字面停下，白跑一轮，**全程不报错**。

同族的旧教训：`0909P` 发版 opener 的「这次发什么」必须现算（08-27 起立）、
接力文档里的 pytest 数字 ⛔ 不许抄进 opener 当基线（【四】）。**本条是它们的统一表述。**

## 引用式 Opener 的由来

*为什么*：① 一份 500+ 字的块复制时容易掉头掉尾，且错了不报错；② opener 只在聊天里派、从不落档，正是 08-27 一天撞号 5 次的根因——
文件化后号池查重 `grep -rho "\[Mac\]MMDD[A-Z]" docs/openers/` 自动命中；③ 与「企业AI转型」侧「CC 交接用文件引用、不贴长 prompt」同一原则。
⚠️ 引用式把「内容漂移」换成「路径失效」——所以引用块里要带"文件不存在即停"，⛔ 不许 CC 凭标题脑补。

## 引用式 Opener 死链实证（0909AS）

**实证**（2026-09-10）：`[Mac]0909AS` 贴出了 `[Mac]0910A` 的引用块，但被引文件**从未创建**、号也**未登记**台账
⇒ 接手 session 按「文件不存在即停」停下，零产出。引用式 opener 退化成**死链**时，接手方既读不到正文、
又在号池里查不到号，且**全程不报错**——这正是上一条判据要挡的。见 `docs/session接力.md` AS-1／AS-2。

## 自动化三条的由来实证（0909AG／TD-39）

*实证*：`0909AG`（TD-39 断线复核）初版写的是「你手动关一次 Wi-Fi、90 秒后再开回来」，
被他当场退回。改自动化之后**证据反而更好**——2 秒一次采样能算出 `liveness` 到底几秒翻，
人眼盯着算不出来。

## 无人值守禁止提问的由来

*为什么*：本项目已经在用 `/loop`、`ScheduleWakeup` 这类无人值守重新触发的机制，将来还会有"每天检查 `.51` 服务是否存活"这类定时巡检。企业AI转型的巡逻 prompt 至今恰好没有提问句，但那**纯属惯例、规则从未写下**——一旦有人复制交互式模板去建定时任务，提问句就会被带进去。口径同 `CLAUDE.md`「无人值守 prompt 禁止提问」。

## 收工段两项要求的由来

> *为什么*：这件事我们每次都在收工时手工重做一遍。更实际的问题是**未提交悬置**——
> Cowork 根本不能提交（bash 在隔离 VM 里，对 `.git/` 只能写不能删），
> 改动只能靠人复制清单到 Claude Code tab；清单不全，漏掉的文件就永远停在工作区。
> 任务再小也不例外——只改一个字也要列出那一个文件，"小改动不用列"正是漏提交的来源。

## 一律新开 session 的原因

**为什么一律新开 session**：上一阶段的会话里塞满了它自己的产物与推理，接着用会把新任务锚定在旧结论上。重跑一份计划时尤其明显——旧会话会不自觉地复述旧计划。OpenSpec 官方也建议实现前清空上下文。

## 人守守不住——机器判据落点

🔴 **人守守不住，已上机器判据**：那边这条规则**定下当天就被违反 17 次**——根因不是没载体，
规则就写在起草者当天亲手编辑过两次的文件里、位置在正上方 40 行。⇒「读到规则 ≠ 执行规则」。
本仓库的落点＝`scripts/hooks/check-opener-header.py` 判据②：
**代码块的【设置】写着「执行环境: CC」却无 `set_session_title` → `exit 2`**。
Cowork 块不判（那边没这个工具）。
