## 零、为什么

2026-10-01 00:0x，Shao Peishen 在值守群里看到两条回推通知，正文是

```
【值守通道·新任务已登记】

```

——`thread_id`／`msgid` 是内部不透明标识，直接甩给群里的人看不可读。他要求改成可读文案（2026-10-01 提）。

⛔ 不发任何真实消息、⛔ 不重启值守、⛔ 不改判据/其它模块、⛔ 不碰凭据。

## 二、新文案（照这个形状，字段值由调用方给）

```
【值守通道·新任务已登记】
来源：邵培申（群消息）
时间：2026-10-01 00:02
摘要：@MAC机器人 回写验证
追踪号：e3015852
```

判据：

1. `来源` ＝ **人名** ＋（`群消息`／`私信`）——人名从既有 `load_whitelist_names(ports.whitelist_path)`
   映射取（`userid → name`）；取不到时**回退 `sender_userid`**（⛔ 不许直接抛）。
   渠道标签由调用方用既有 `frames.frame_chattype(frame)` 判定后传入，
   ⛔ **不许用 `thread_id` 的形状去猜**（私信 thread_id 就是 userid，猜必错）。
2. `时间` ＝ CST 的 `YYYY-MM-DD HH:MM`（分钟精度）——由调用方从 `moment` 产出
   （可复用 `session.format_instant(moment)` 再裁到分钟；⛔ 不新造第二套时区/格式化逻辑）。
3. `追踪号` ＝ `msgid` **前 8 位**（grep 得到，够对账；⛔ 不再出现完整 32 位 msgid）。
4. ⛔ 文案里**永远不出现**完整 `msgid`、完整 `thread_id`、webhook 地址或任何凭据。
5. 纯函数签名改成：`compute_task_relay_text(*, sender_label: str, channel_label: str, occurred_at: str, msgid: str, summary: str) -> str`
   （工程铁律 2 的形状：⛔ 不读时钟、不记日志、不碰库；时间字符串与渠道标签都由调用方传进来）。
6. `摘要` 的语义不变（仍由 `queue.compute_task_summary` 机械截断，⛔ 不改成正文）。
