【三、要做什么】

### 3.1 🔴 先读懂 `__main__.py` 的线程与事务纪律 —— 违反它这条就白做了

`tools/liaison/__main__.py` 里有一条**贯穿全文件的硬纪律**，注释里逐字写着：

> 回调只做一件事：把 `(事件名, 当时的时间)` 放进队列，与连接事件回调同一纪律——⛔ 不碰库、不碰文件。
> 主线程被 `client.run()` 占着（它内部 `loop.run_forever()`），**值守线程独占库**。

⇒ **`message` 回调 ⛔ 绝对不许直接调 `handle_inbound_message`。**
它必须走同一条路：**SDK 回调 → 塞队列 → 值守线程（持有那条唯一的库连接）取出来再调**。

*为什么*：`handle_inbound_message` 会写 `liaison_message` / `liaison_task` / `effect_log`。
在 SDK 的事件循环线程里直接写，等于让第二个线程碰同一条连接——这正是
`docs/findings/2026-08-13-sqlite-事务归属冲突.md` 记的那个坑，
现网 08-10 与 08-12 各丢一轮 `outbox`。**工程铁律 1 的失效方向：幂等记录成功、业务写失败 ⇒ 永不重试。**

⚠️ 队列里放的东西要够 `handle_inbound_message` 用（`thread_id` / `msgid` / `sender_userid` /
`received_at` / `msgtype` / `content` / 附件），但**回调侧 ⛔ 不许做任何 IO**——
附件下载这类要么在值守线程里做，要么这一轮先不做并在报告里点名。

### 3.2 接线本体

1. `session_client.py`：给 `message` 事件加常量并进 `SUBSCRIBED_EVENTS`
   （当前是 `(EVENT_CONNECTED, EVENT_DISCONNECTED, EVENT_ERROR, EVENT_AUTHENTICATED)`）。
   ⚠️ **事件名以 SDK 源码为准，⛔ 不许猜**。`session_client.py` 里已有
   `verify_sdk_activity_markers` 那套"启动时核对文案仍在 SDK 源码里、不在则拒绝启动 exit 4"的做法，
   **本条照抄同一纪律**：事件名核不到就 raise，⛔ 不许静默订阅一个不存在的事件
   （漏订阅不报错，只是永远收不到——又一个无症状故障）。

2. `__main__.py`：注册 `message` 回调 → 入队；值守线程侧取出 → 调 `handle_inbound_message`。

3. `message` 事件同样要**刷 `last_event_at`**（TD-42 的判据）——收到真实消息当然算 SDK 活动。
