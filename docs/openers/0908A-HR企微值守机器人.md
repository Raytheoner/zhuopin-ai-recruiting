【背景】
HumanResource 本来就是"企业AI转型"项目的部门模块之一。那边的采购/财务/质量三个部门都有专职 AI 专员，通过企微"智能机器人"（aibot）24 小时值守收材料、传信息，服务源码在 `5-平台底座/wecom-aibot-service/`（架构、六个真实生产 bug 清单，本仓库 `06-企业AI转型资产借鉴清单.md` §三已有完整分析，直接看，不要重新调研）。

HR 侧对应的专员已确认：**汤丽萍**。已有一个企微群"人力AI保障组"（成员：邵培申/陈承/聂鑫/汤丽萍/王寒月），双方目前在这个群里手动交换材料（例：`岗位要求确认反馈表v3.xlsx`）。

决定：把这套值守机制迁到 Mac，在 HumanResource 仓库里**独立实现**（不跨仓库引用/拷贝 wecom-aibot-service 的代码，只读参考做法）。原因：Windows 那台机器上的现有开发模块即将结束使用，Mac 是今后的主力开发机，一定要转移。

架构上 Windows 与 Mac 两边**各自独立运行、各管各的白名单和任务队列**——Windows 继续管质量/采购/财务，Mac 新建的这一套只管 HR，两边不共用同一个企微 aibot 的 BotID/Secret。理由：企微"智能机器人"是 WS 长连接协议，同一个 BotID/Secret 是否允许两台机器同时建长连接，没有查到官方文档确认，也没有把握用测试验证清楚（可能的失败模式包括消息重复投递、后连的顶掉先连的、或直接被拒），过渡期 Windows 那套还在服务现役部门，不值得为了省一次注册去冒这个不确定的风险。**Mac 这边独立注册一个新的 aibot 应用**，BotID/Secret 留空由 Shao Peishen 自己在企业微信管理后台申请后填入 `.env`，本次 proposal 不涉及凭据本身。

【已做的技术侦察，直接可用，不要重新调研】
- wecom-aibot-service 架构与真实生产 bug：`06-企业AI转型资产借鉴清单.md` §三（3.1-3.5）。要点：白名单是硬编码 `frozenset`、fail-closed；消息落地是 append-only 归档、`msgid` 只做归档文件名去重、**没有真正的幂等键**；至少六个真实生产 bug 里"归档文件名按天粒度导致同人同天多条消息互相覆盖""二进制文件被当文本做 UTF-8 解码校验误判损坏"这两类最容易在新实现里重蹈。
- 参考代码只读，来源已迁移到 GitHub（`https://github.com/Raytheoner/zhuopin-ai-transformation`，分支 `master`，路径 `5-平台底座/wecom-aibot-service/`，中文路径要 percent-encode），用 `WebFetch` 读，没有本地副本不能 grep 模糊搜索，引用它时必须给到文件级路径。
- 本项目工程铁律 6「企微回调先落库再处理：只推一次、5 秒无响应即丢弃。回调接口只做签名校验+落库+返回200」是针对 HTTP 回调模型写的；wecom-aibot-service 走的是 WS 长连接协议，没有"签名校验"这一步，这条铁律的落地方式需要按 WS 协议特性重新设计，不能照抄字面。
- 工程铁律 1（幂等 effect 节点 + `effect_log` 表 + 唯一索引）是本仓库现成机制（`app/graph/nodes.py` 的 `@idempotent_effect` 装饰器、`app/storage/db.py` 的 `effect_log` 建表），这套服务的消息处理落库应该复用同一套设计思路，不要另起一套幂等机制。
