【背景】
`app/audit/assertions.py` 的断言四（`assert_every_decision_has_human_review`，对应合规红线「淘汰必须有人工确认节点并留痕」的机器判据）有一个真实缺口，已在 0904C 交付时发现并如实登记，Shao Peishen 2026-09-04 已裁决「现在修」：

问题原文见 `openspec/changes/m1-job-profile-intake/tasks.md:193`（`Task 8 parked` 那条）：豁免用 `job_profile.created_at`（画像草案创建时间）与 `HUMAN_REVIEW_ENFORCED_FROM`（2026-09-04 00:00:00）比较；但 `effect_confirm_profile` / `effect_abandon_profile` 是就地 `UPDATE status`，不会推进 `created_at`。后果：部署时刻已存在的所有 `job_profile` 行，不论以后哪天被确认/放弃，永远落在豁免侧——这批行日后若被确认却漏写 `human_review`，断言四完全看不见，等于给这批数据开了个永久盲区。

当前实现见 `app/audit/assertions.py:262-338`（`HUMAN_REVIEW_ENFORCED_FROM` 常量与 `assert_every_decision_has_human_review` 函数本体）。

【已做的技术侦察，直接可用，不要重新调研】
`app/storage/db.py:59-65` 的 `effect_log` 表已经有你需要的东西，不用加新列：

```sql
CREATE TABLE IF NOT EXISTS effect_log (
    effect_key TEXT PRIMARY KEY,
    thread_id TEXT NOT NULL,
    node_name TEXT NOT NULL,
    business_key TEXT NOT NULL,
    applied_at TEXT NOT NULL
);
```

`app/graph/nodes.py:233` 与 `:337` 分别是 `@idempotent_effect("effect_confirm_profile")` 与 `@idempotent_effect("effect_abandon_profile")`，每次真正执行确认/放弃动作都会在这张表留一行、`applied_at` 就是决策发生的真实时刻（工程铁律 1 的产物，不是新造的机制）。

方向：断言四不该拿 `job_profile.created_at` 跟截止日比，应该拿**这条决策对应的 `effect_log.applied_at`**跟截止日比——用 `node_name`（按 status 选 `effect_confirm_profile` 或 `effect_abandon_profile`）+ 能定位到具体 job/version 的 key 去关联。`effect_key` 的组装规则、`business_key` 具体存的是什么值（`nodes.py:389` 附近注释提到"business_key = 被确认的画像 version"，但同一 version 号可能跨 job 重复，要不要一并核对 `thread_id`/`job_id` 的对应关系）留给你在这一步核实清楚——这是这次要更新的规格里必须讲清楚的设计点，不要含糊过去。
