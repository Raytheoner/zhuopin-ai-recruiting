【二、缺陷是什么（已定位到行，⛔ 不必重新调查）】

连接断开后 SDK 只重连一次；那一次失败时抛出的异常，会把**唯一还能触发重连的 task** 杀死，
于是永不再试。进程仍活着、`liveness.json` 永远停在 `disconnected`、中断窗口永不闭合、
恢复告警永不发出——**服务看起来在跑，其实早断了**。

根因链（SDK `wecom_aibot_python_sdk 1.0.2`，行号为 venv 内实际行号）：

1. `aibot/ws.py:149-153` `connect()` 失败分支：
   ```python
   except Exception as e:
       self._logger.error(f"Failed to create WebSocket connection: {e}")
       if self.on_error:
           self.on_error(e)              # ← 152 行，在这里炸
       await self._schedule_reconnect()  # ← 153 行，永远走不到
   ```
2. `aibot/client.py:76`：`on_error` 被接成 `lambda error: self.emit("error", error)`；
3. `pyee/base.py:178-184` `_emit_handle_potential_error`：**`error` 事件没有监听器时直接 `raise`**；
4. `tools/liaison/session_client.py:214-215` 只接了两个事件，**没有 `client.on("error", …)`**
   ⇒ 第 3 步必抛 ⇒ 152 行炸 ⇒ **153 行永远走不到**；
5. 异常冒泡出 `_receive_loop()`（`ws.py:208`），该 task 死亡
   （`Task exception was never retrieved`）。它是唯一还会调 `_schedule_reconnect` 的地方。

🔴 **还有第二层（N-0，⛔ 不许只修第 4 步就收工）**：`session_client.py:258-262` 的注释写
「`client.run()` 几乎不会返回 …… 外层 `run_forever` 是**兜底**那一层」。本故障下这条假设
**不成立**：task 死后 `loop.run_forever()` 照样挂着 ⇒ `client.run()` **仍然不返回** ⇒
外层 `run_forever` 永远等不到那次返回，**兜底一次都不会触发**。
⇒ **两层重连被同一个异常一并打掉。** 只补监听器能修好这一条路径，但兜底层依然是空的：
SDK 里任何别的「task 死了但 loop 还活着」的形态都会原样重演。

⛔ **不要改 `max_reconnect_attempts`**：`session_client.py:145` 已经传了
`UNLIMITED_RECONNECT_ATTEMPTS`（`= -1`），`ws.py:341` 的放弃分支对 `-1` 直接短路。
（tech-debt 初版的 N-1 说要改成 `-1`，那条**已作废**，见 TD-39 的订正段。）
实测只重连 1 次是因为 task 死了，**不是**次数用尽。

【三、要改什么（TDD：先让测试红，再改实现）】

🔴 **每一项都必须先写出一条在当前代码下真的红的测试，跑一遍看见它红，再动实现。**
⛔ 不许"改完实现顺便补个测试"——那样你不知道测试到底有没有判据力。
本条守的正是**无症状**故障：没有真能失败的测试钉住，它下次回归时同样不会有任何症状。
⚠️ 现成的反面教材：TD-38 那条断言 `assert options.heartbeat_interval == DEFAULT_HEARTBEAT_SECONDS`
是同义反复，单位错成什么样它都绿——**这正是那个 bug 活到真实建连才暴露的原因**。

**改法 1（根因）**：在 `_prepare_client` 里补 `error` 事件监听器。

- 语义：**记日志，不重新抛出**。让 pyee 走"有监听器 ⇒ 分发不抛"的分支，
  `ws.py:153` 的 `_schedule_reconnect()` 就能正常执行。
- ⚠️ 日志要走 `logsetup` 的脱敏通道（`tools/liaison/logsetup.py`），
  ⛔ 异常文本里可能带 URL/凭据片段，不许裸 `print` 或裸 `logging`。
- ⛔ **不要吞掉之后当没事发生**：至少 `WARNING` 级，且写清"已交给 SDK 重连"。
- 事件名建议提成模块级常量（与 `EVENT_CONNECTED` 并列），并**纳入
  `verify_client_surface` 的事件校验**——它现在只核那两个事件，
  漏掉 `error` 正是本条能发生的原因之一。

**改法 2（N-0 兜底）**：补一条基于 `liveness.json` `stamp_at` 的看门狗。

- 判据：`stamp_at` 超过阈值没刷新 ⇒ 认定"loop 还活着但连接已死" ⇒ 主动断开重建，
  让外层 `run_forever` 真的能接手。
- 阈值⛔ 不要拍脑袋：实测判死时延是 **55.75 秒**（心跳 30 秒 × 2 个未回 pong），
  阈值必须**明显大于**它，否则会把正常的判死过程误判成假死、造成无谓重建。
  取值写进常量并在注释里写明这个 55.75 秒的实测依据。
- ⚠️ **看门狗自己不能成为新的静默故障源**：它挂了要有症状。
  ⛔ 不许写成"异常就 pass"。

**改法 3（测试，🔴 本条的重头戏）**：至少覆盖三条，全部用替身、⛔ 不碰网络。

1. **回归钉子（对应根因）**：造一个替身 client，其 `on_error` 走 pyee 的真实语义
   （没有监听器就 `raise`）。断言 `_prepare_client` 之后，触发 `error` 事件
   **不会**把异常抛出去。⚠️ **这条必须在当前代码下真的红**——先跑一遍确认。
2. **重连链不被打断**：模拟"连接失败 → `on_error` → `_schedule_reconnect`"这条序列，
   断言 `_schedule_reconnect` **被调用到了**。这条钉的是"152 行炸掉 153 行"那个具体形态。
3. **看门狗（对应 N-0）**：`stamp_at` 陈旧到超过阈值时，断言触发了重建；
   在阈值内则**不**触发。⚠️ ⛔ 不许用真实 `sleep` 等时间过去——注入时钟。

⛔ **不要为了让测试好写就改动 `verify_client_surface` 的严格性**：它是整条链上唯一的护栏，
`session_client.py:149` 的 docstring 明写"⛔ 不许删、不许加跳过校验的开关"。
