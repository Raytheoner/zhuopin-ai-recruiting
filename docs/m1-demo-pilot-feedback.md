### 反馈 2、3 的调查（Shao Peishen 用服务器真实数据核对，2026-08-18）

两份反馈都提到"画像/JD 有欠缺"和不同程度的"重复问同一件事"，没有停在"经理这么说"就记下了事——SSH 到 51 服务器，直接查 `data/demo.db` 里这两个岗位的 `job_profile` 逐轮快照和 `conversation` 完整对话记录，核对了三件事：

1. **"东风风神"不是编造，是真的漏看了该截图哪一页**。两位经理在表单第 2 题（编造检查）里贴的图，实际都是**生成后的 JD 文本截图**，不是表单明确要求的"确认画像"那一页截图（表单原话："把'确认画像'那一页整页截图，直接贴进下面这个框"）。这意味着表单设计想要的"圈出画像里的编造内容"这个核对动作，两位经理实际上都没有针对真正该核对的页面做——他们看的是最终成文的 JD，不是结构化字段列表，更不容易发现字段级别的编造（连续的文案比一份字段表更难挑错）。**这是流程执行偏差，不是系统 bug**，但说明 `docs/m1-demo-manager-guide.md` 第 2 题的说明可能需要更醒目/更难跳过（比如直接把"确认画像"那一步单独截一次图的提示放在追问对话最后一步旁边，而不是靠陪同人员口头提醒）。
   - 核对方法：反查 `2494103e...` 这个采购岗位的 `conversation.history_json`，逐轮读用户真实输入，第 6 轮用户原话就是"东风风神；谈判，协同；ecu相关经验"——AI 只是把这句话正确映射进了 `project_experience_requirement` 字段，没有任何编造。
2. **"重复问同一件事"是两种不同的真实模式，都不是 2026-08-11 已经修过的那种"一字不差原样重发"**：
   - **采购岗位（16949/26262）**：用户没有一次性答全"IATF 16949 具体要求"和"是否需要 ISO 26262"这两个子问题，AI 后续轮次把没答的子问题换了个措辞、跟别的新问题捆在一起重新问——文字不同，但话题重复，用户体感就是"问过了怎么又问"。这不是幻觉/bug，是当前"每轮打包问 2-3 个问题、答不全就换个说法追"这个设计策略在多子问题场景下的固有代价，2026-08-11 修的"逐字重复检测"抓不住这种情况（因为原文不一样）。
   - **软件岗位**：核心问题不是重复措辞，是用户在某一轮回了"这些我不太了解，你有什么建议"，AI 给的回复是一句空泛的"您可以按建议补充岗位要求……我来帮您整理"——**没有真的给出任何具体建议，也没有提取到任何新字段**，白白浪费了一整轮（`profile_patch` 这一轮和上一轮完全相同）。这直接导致后面轮次不够用，`toolchain`／`soft_skill_keywords`／`functional_safety` 这几项最终都进了 `unspecified_fields`，对应上了经理"工具链要求缺失、软技能未提、加分项偏单薄"的抱怨。**这是一个值得修的真实产品缺口**：用户明确表示"不知道""你有什么建议"时，系统应该给真正可选的默认建议（比如列 2-3 个该领域常见档位供用户选），而不是一句空话又把同样的问题原样扔回去。
3. **`unspecified_fields` 有被系统正确记录，但业务经理容易看不到/不当回事**：两份画像最终都在 `MAX_ROUNDS=5` 命中时被强制收尾，未确定的字段（软件岗：`headcount`/`functional_safety`/`soft_skill_keywords`/`toolchain`/`sop_projects`；采购岗：`autosar_experience`/`sop_projects`/`diag_stack`）都正确写进了 `unspecified_fields`，前端也确实把它渲染成了"以下字段未指定：……"这行提示（`app/web/static/index.html:49-52`）。但这行提示混在对话流里，字段名是英文 snake_case（如 `functional_safety`），不是显著的、贴着"确认画像"按钮的警示。两位经理最后都点了确认，事后还是在 JD 里发现同样的缺口——说明这条提示实际上没有真正引起注意、促成"回去补答"的行动。**建议**：确认画像前，把 `unspecified_fields` 渲染成中文人话 + 视觉上更显著的警示块，而不是聊天记录里的一行小字。

**这三条发现建议在进 `tasks.md` 第 1 章前排进技术债优先级**（尤其第 2 条"我不知道/你有什么建议"式回答的兜底逻辑，直接影响画像完整率）。

#### 更正（2026-08-19）：第 2 条的根因归属不完整——还有第三种模式，是系统真的把消息丢了

上文把"重复问同一件事"归成两种模式（未答子问题被换措辞重问 / 空转轮），并判定前者是
"当前追问策略在多子问题场景下的固有代价"。**这个判断不完整。** 同一套代码在现网已被
证实存在**第三种**模式：`effect_deliver_message` 的业务写丢失——幂等记录写成了、
`outbox` 那行没写进去，用户压根没收到上一轮回复，于是把话再说一遍；模型从 checkpoint
里读到自己确实问过，判定是自己重复了，便道歉并换措辞重问。

证据见 `docs/findings/2026-08-13-sqlite-事务归属冲突.md` §8.5：`1cabfb91`（08-12）与
`41909b40`（08-10）各丢一轮，**两个 thread 丢失轮的下一条 `outbox` 都以「抱歉，刚才的
问题重复了……」开头**——AI 在为一次它以为自己犯的重复道歉，真实原因是用户没收到上一轮。
而且这次丢失不可恢复：幂等键已落库，重放会判定"已投递"而静默跳过。

**pilot 期间跑的是有 bug 的版本。** 三次真实试跑落在 2026-08-13~08-18、反馈收集到
08-18，而修复 2026-08-18 13:04 才部署到 `.51`（findings §8.4）——**全部会话都跑在修复前
的代码上**。三份反馈的归因都要因此打一个折扣——不是"经理说错了"，是"系统当时本身不可信"。

**但要说准确，别把折扣打过头：**

- 三份反馈对应的会话（反馈 1 供应链 `a478499c` 08-13 / 反馈 2 软件 `19b6ec6d` 08-18 /
  反馈 3 采购 `2494103e` 08-18）**自身的两条原子性不变式都是绿的**，没有查到丢消息。
  已证实的两次损伤（`1cabfb91` 08-12、`41909b40` 08-10）都发生在这三个会话之前。
  **目前没有证据表明 pilot 反馈里的"重复问同一件事"就是投递丢失。**
- **但绿不等于没丢。** 不变式只抓得住"幂等写与业务写一个成一个败"。若某一轮两边恰好一起
  失败，这一轮会整体消失、计数仍然相等，数据上不可见。绿是弱证据，不是证明。

**净结论**：pilot 报的"重复问同一件事"，最可能的解释仍是上文第 2 条的两种模式；但
"这是追问策略的固有代价"这句话**不能再当成唯一解释**——已经证实存在一个会产生完全相同
表象的基础设施故障。修复上线后的回填验证（`m1-intake-quality-fixes` proposal 的 Impact
已列本文件）要顺带把这两种表象分开：先按不变式确认该会话没丢消息，再谈追问策略。

#### 🔴 这个 0 能说什么、不能说什么

1. **样本量：3 段会话 / 18 轮 / 26 个字段。⛔ 不可外推。** `design.md` 决策 12 定死的门槛是
   **累计 ≥ 20 场真实采集会话**才谈拦截阈值——现在是 **3 场**，连零头都不到。
   ⛔ 不得据此改任何拦截逻辑，也⛔ 不得对外说"flash 不编造"。
2. **0 是"下界为 0"，⛔ 不等于"确认没有编造"。** 判定是确定性子串匹配，已知三条**偏低**来源
   （`docs/m1-fabrication-rate.md`「这个数字是下界」）：① `normalize_for_grounding` 去掉全部空白
   让英文词边界消失；② 点选提交会把问题原文连同所有档位一起拼进用户消息，未被勾选的档位也能被引用命中；
   ③ `_coerce_quote` 不设最小长度门槛，单字引用（"的""要"）在中文原话里几乎必然命中。
   三条都让真实编造率 **≥** 这里算出的数字。
3. **人工抽查这一步这次没有对象。** `design.md` 风险表要求"回放真实会话时人工抽查若干未溯源字段，
   区分模型不会引用与模型真编造"——**分子为 0，没有未溯源字段可抽**。⏸ 这一步顺延到下一批
   拿到非零分子时做，⛔ 不因"抽查通过"记功。
4. **和 `deepseek-v4-pro` 的 1/3 ⛔ 不可直接相减。** `docs/m1-model-comparison.md` 那个 1/3 是
   **人工核对**得出的，本表是**引用判定**得出的，两个口径。可比的只有同口径的前后两次
   （换模型前后、改提示词前后）——**本表就是那个"前"**。

> **为什么专门问等待和编造这两项**
>
> **等待**：实测单次 LLM 调用 7~26 秒，5 轮追问 + JD 生成大概率累计 40~70 秒。这个数字看着难受，但业务经理的参照系是"以前提个需求要跟 HR 来回沟通几小时甚至几天"——等一分钟可能完全可以接受。**在拿到真实反馈前不要动手优化**，那是凭数字想象痛感。问法上别问"快不快"（人会客气），问"等的时候你在想什么"。
>
> **编造**：`deepseek-v4-pro` 实测 3 次里有 1 次凭空抽出了输入完全没提到的 MCU 型号与工具链（ARM Cortex-M / Infineon TriCore / Keil / IAR）。画像里多出业务经理没说过的硬性要求 → 寻源方向偏 → 后面全白做，而且很难被发现。这一项比准确率更要紧。
