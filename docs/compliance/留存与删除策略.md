# 简历与评分数据留存与删除策略

适用范围：`m2-resume-parse-and-rank` 处理的候选人简历原文、结构化抽取结果、AI 评分记录、投递状态流转记录。对应 `docs/roadmap/定夺队列.md` Q-02。

## 一、留存范围与期限（草案，待法务确认具体期限数值）

| 数据类别 | 存储位置 | 拟定留存期限 | 依据 |
|---|---|---|---|
| 简历原文（PDF/DOCX/扫描件） | Postgres（`.51`，不出境） | 候选人同意的招聘流程结束后 <待定：拟 N 个月> | PIPL 最小必要原则 |
| 结构化抽取字段 | Postgres | 同简历原文 | 与原文同生命周期 |
| AI 评分记录（`criterion_score` 及 `evidence_ref`） | Postgres | 同简历原文，且不早于相关 `rejection_record`/录用决定的留存期限 | 工程铁律 3/4 要求评分可追溯 |
| 投递状态流转（`application_stage_history`） | Postgres | 与所属 `application` 同生命周期 | 数据模型要点：流转事实表是报表基础 |
| 企微回调原始记录 | `effect_log` 及回调落库表 | 与所属节点的幂等窗口一致，另按数据类别留存期限清理 | 工程铁律 6：回调先落库再处理 |
| 简历访问留痕（谁在什么时候看了谁的简历） | 独立审计表 | 长期保留，不随简历本体删除而清除 | M2 门槛：PIPL 可查性要求，审计记录本身不含额外个人信息处理目的 |

## 二、删除触发条件

1. **候选人主动行使删除权**（见《候选人同意条款》第二条）：收到申请后在法定/约定时限内完成删除，简历原文、结构化字段、AI 评分记录一并删除；投递状态流转记录按脱敏方式保留统计口径，不保留可识别到人的字段。
2. **留存期限届满**：达到上表期限自动触发删除流程，非人工逐条判断（避免遗漏）。
3. **候选人明确要求仅撤回同意、不要求删除**：停止后续处理，但既有记录按留存期限走正常流程，不额外提前删除。
4. **投递流程终止且候选人未再互动超过留存期限**：视为期限届满，按第 2 条处理。

## 三、删除执行方式

- 删除操作本身是一个有副作用的动作，须独占节点、带幂等键，避免重复执行或漏执行（工程铁律 1）。
- 删除范围**必须覆盖**：简历原文文件、结构化抽取字段、AI 评分记录（含 `evidence_ref` 回指的原文片段，因其依附简历原文，原文删除后 `evidence_ref` 同步失效或一并清理）。
- 删除范围**不覆盖**：简历访问留痕审计表（用于满足 PIPL 可查性要求的独立记录，不属于候选人个人信息的"处理"范畴，仅记录"谁在何时访问"）。
- 删除执行后需可核验：审计表记录本次删除操作的执行人/时间/触发条件，供后续合规检查追溯。

## 四、数据边界与工程铁律对齐

- 回调数据先落库再处理，只推一次、5 秒无响应即丢弃（工程铁律 6）——本策略中"企微回调原始记录"的留存期限独立于其触发的业务记录，避免因回调重放判断需要而无限期保留。
- `application` 与 `candidate` 为独立实体，删除候选人数据时须同时处理其名下所有 `application` 记录，不得因实体独立而遗漏关联删除。
- 幂等记录（`effect_log`）与业务写同事务提交（工程铁律 1）——删除操作若涉及跨表级联，同样须保证事务一致性，不允许"简历原文已删、评分记录未删"的中间态持久化落盘。
