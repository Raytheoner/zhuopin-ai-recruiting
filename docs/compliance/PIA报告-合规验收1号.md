# 个人信息保护影响评估（PIA）报告 —— 合规验收 #1

适用范围：`m2-resume-parse-and-rank`（M2 阶段，简历解析与排序），处理真实候选人简历数据前的前置评估。对应 `docs/roadmap/定夺队列.md` Q-02。

## 一、处理目的

- 为卓品智能（无锡 ECU/汽车电子研发制造企业）嵌入式/汽车电子工程师岗位招聘提供简历解析、结构化抽取与基于岗位能力 rubric 的排序推荐。
- AI 输出仅作为招聘专员筛选简历时的**排序参考**，不构成录用或淘汰决定。

## 二、处理范围

- **处理的数据**：候选人简历原文（PDF/DOCX/图片扫描件经 PaddleOCR/MinerU 抽取）、结构化字段（教育、工作经历、技能关键词）、AI 评分结果（`criterion_score` 及 `evidence_ref`）、投递状态流转记录（`application_stage_history`）。
- **不处理**：人脸/表情图像分析（合规红线明令禁止）、历史录用结果作为监督信号。
- **数据不出境**：全部模型走境内部署（技术栈：境内 LLM schema 抽取 + BGE-M3 + FunASR/CosyVoice，阶段二），简历原文与派生数据均落于自建 Postgres（`.51` 服务器），不经境外 API 中转。
- **数据边界**：`application` 与 `candidate` 为独立实体（数据模型要点），状态数据不与候选人身份数据混同存储于同一冗余字段。

## 三、AI 评分用途与限制

- AI 评分只用于**排序推荐**；淘汰必须有人工确认节点并留痕（合规红线：`rejection_record` 中 `reason_type='ai_score'` 的记录数恒为 0，此断言须有测试覆盖）。
- 每条 `criterion_score` 必须有 `evidence_ref`（回指简历原文或面试 turn 的 offset），为空不允许写入（工程铁律 4）。
- 主观描述（如"沟通能力强"）不进入硬门槛规则，只作为软技能关键词展示（合规红线）。
- 声学情绪信号（语速/停顿/静默）仅展示给面试官，不进入 `criterion_score`（合规红线，声学≠人脸/表情，人脸识别分析全面禁止）。
- 绝不用历史录用结果做监督信号，只用显式岗位能力 rubric（合规红线，对应 Amazon 2018 教训）。

## 四、风险点与缓解措施

| 风险 | 缓解措施 |
|---|---|
| AI 评分被误用为自动淘汰 | 架构上淘汰节点强制人工确认+留痕；审计断言 `reason_type='ai_score'` 恒为 0 |
| 评分不可追溯、无法复核 | 工程铁律 3：模型标识+版本+prompt 版本+temperature+输入哈希+rubric 快照+原始响应全部持久化；供应商给漂移别名（如 `deepseek-chat`）时以响应实际返回的 `model` 字段为准 |
| 简历数据出境 | 全链路模型境内部署，架构评审锁定 |
| 候选人身份泄露/越权访问 | M2 起处理真实简历前必须具备可识别到人的登录 + 简历访问留痕（PIPL "谁在什么时候看了谁的简历"可查），共享口令不满足 |
| 企微回调重复处理/丢失 | 回调先落库再处理，只推一次、5 秒无响应即丢弃；回调接口只做签名校验+落库+返回 200（工程铁律 6） |
| 节点重跑导致重复副作用（如重复发消息、重复建工单） | 每个有副作用的节点带幂等键 `{thread_id}:{node_name}:{business_key}`，落 `effect_log` 并加唯一索引；幂等记录与业务写同事务提交（工程铁律 1） |
| AI 生成内容未标识误导候选人 | AI 生成的 JD、拒信、邀约须带标识（《AI 生成合成内容标识办法》2025-09-01 施行） |
| 候选人入口被认定"向境内公众提供" | 候选人入口一律用一次性邀请链接 |

## 五、对合规红线七条的逐条自查

1. AI 只做排序推荐，不做自动淘汰 —— ✅ 架构约束 + 审计断言覆盖
2. 禁止人脸/表情分析 —— ✅ 未引入该能力，声学情绪信号限定展示范围
3. AI 生成内容须带标识 —— ⏳ 待 JD/拒信/邀约生成模块实现时落地，M2 本阶段暂不涉及
4. 模型全部走境内，数据不出境 —— ✅ 技术栈选型已锁定
5. 绝不用历史录用结果做监督信号 —— ✅ 仅用显式 rubric
6. 候选人入口一律一次性邀请链接 —— ⏳ 待候选人对外通道模块实现时落地
7. 主观描述不得进入硬门槛规则 —— ✅ 仅作软技能关键词
