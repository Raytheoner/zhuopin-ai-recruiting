### 断网脚本原文（`/tmp/ag/outage.sh`）

⚠️ 与 opener 正文的差异**只有一处**：采样 SQL。opener 写的是
`select id,started_at,ended_at from liaison_outage_window`，而真实 schema 里
**没有 `id` 列**（主键是 `started_at`），闭合列叫 `recovered_at` / `closed_by` 而非 `ended_at`。
照抄会每次采样都报 `no such column: id`，等于全程采不到窗口数据。已按真实 schema 改写。

```bash
#!/bin/bash
DEV=en1
LOG=/tmp/ag/samples.log
DB=/Users/paulshao/Projects/HumanResource/data/liaison.db
LV=/Users/paulshao/Projects/HumanResource/data/liaison/liveness.json
# (1) 独立兜底：本脚本即使被 SIGKILL（trap 不执行）也能把网开回来
( sleep 300; networksetup -setairportpower "$DEV" on ) >/dev/null 2>&1 &
disown
( sleep 420; networksetup -setairportpower "$DEV" on ) >/dev/null 2>&1 &
disown
# (2) trap 恢复：正常退出/中断都恢复
restore() { networksetup -setairportpower "$DEV" on; echo "$(date '+%T') RESTORE-TRAP" >> "$LOG"; }
trap restore EXIT INT TERM
sample() {
  echo "=== $(date '+%T.%N') phase=$1 ===" >> "$LOG"
  cat "$LV" >> "$LOG" 2>&1; echo >> "$LOG"
  sqlite3 "$DB" \
    "select started_at,detected_by,recovered_at,closed_by,alerted_at from liaison_outage_window;" >> "$LOG" 2>&1
  tail -3 /tmp/ag/stderr.txt >> "$LOG"
}
echo "### RUN START $(date '+%F %T %Z') ###" >> "$LOG"
for i in $(seq 1 8);  do sample BEFORE;  sleep 2; done   # 断网前基线 ~16s
echo "$(date '+%T.%N') >>> WIFI OFF" >> "$LOG"
networksetup -setairportpower "$DEV" off
for i in $(seq 1 45); do sample OUTAGE;  sleep 2; done   # 断网 ~90s
echo "$(date '+%T.%N') >>> WIFI ON" >> "$LOG"
networksetup -setairportpower "$DEV" on
for i in $(seq 1 60); do sample RECOVER; sleep 2; done   # 复网 ~120s
echo "$(date '+%T.%N') >>> DONE" >> "$LOG"
```

三重恢复保险（脚本被 SIGKILL 时 `trap` 不执行，故另有两条独立兜底）：`trap` ＋ `sleep 300` ＋ `sleep 420`。
实测 Wi-Fi 由脚本正常开回，收尾复核 `networksetup -getairportpower en1` = `Wi-Fi Power (en1): On`。

### 无害预检（权限）

## 五、根因（证据链完整，⛔ 本条只登记不修）

SDK：`wecom_aibot_python_sdk 1.0.2`（`site-packages/aibot/`）。

**一句话**：本项目**没有注册 `error` 事件监听器**，而 `pyee` 在没有监听器时对 `error` 事件是
**抛出**而非丢弃；这个抛出恰好落在 SDK 重连代码 `on_error(e)` 与 `_schedule_reconnect()`
**两行之间**，把重连链整条打断。

链路逐跳（行号为 venv 内实际行号）：

1. `aibot/ws.py:149-153` — `connect()` 失败时：
   ```python
   except Exception as e:
       self._logger.error(f"Failed to create WebSocket connection: {e}")
       if self.on_error:
           self.on_error(e)          # ← 第 152 行，在这里炸了
       await self._schedule_reconnect()   # ← 第 153 行，永远走不到
   ```
2. `aibot/client.py:76` — `on_error` 被接成 `lambda error: self.emit("error", error)`。
3. `pyee/base.py:178-184` — `_emit_handle_potential_error`：
   ```python
   if event == "error":
       if isinstance(error, Exception):
           raise error
   ```
   没有 `error` 监听器 ⇒ 直接 `raise`。
4. `tools/liaison/session_client.py:214-215` — 本项目只接了两个事件：
   ```python
   client.on(EVENT_CONNECTED, lambda *args, **kwargs: on_connected())
   client.on(EVENT_DISCONNECTED, lambda *args, **kwargs: on_disconnected())
   ```
   **没有 `client.on("error", …)`。**
5. 异常从 `_schedule_reconnect()` 冒泡出 `_receive_loop()`（`ws.py:208`），
   该 task 直接死亡（`Task exception was never retrieved`）。
6. `_receive_loop` 是唯一还会调 `_schedule_reconnect` 的地方。它一死，
   **重连永久停止**，而 `client.run()` 的主循环还在阻塞等待，进程于是活着但失聪。

**为什么这次才暴露**：TD-38 未修时连接活不过 44 秒就被限流踢断，
每次都是启动路径重建连接，从没走到"运行中断线 → 重连失败"这条分支。

### 次生问题（同批登记，不在本条修）

- **N-1｜重试上限会导致永久放弃**：`ws.py:68-69` `reconnect_base_delay=1000`、
  `max_reconnect_attempts=10`，退避上限 30 秒。即便根因修好，10 次退避总计约
  **181 秒**后打出 `Max reconnect attempts reached …, giving up` 并**永久放弃**。
  值守通道遇到超过 3 分钟的断网（换网、路由器重启、机房割接）同样会静默死掉。
  应改为无限重试（`max_reconnect_attempts=-1`，SDK 已支持该哨兵值）。
- **N-2｜退避首跳撞在断网期**：attempt 1 固定 1 秒后重试，必然落在断网窗口内，
  等于把 10 次机会里的头几次浪费掉。
- **N-3｜`websockets` 库次生崩栈**：`websockets/asyncio/client.py:741`
  `if 200 <= response.status_code < 300:` 在 `response is None` 时抛
  `AttributeError: 'NoneType' object has no attribute 'status_code'`（`connection_lost` 回调里）。
  属第三方库自身缺陷，不是主因，但会污染日志、干扰定位。
- **N-4｜本机走 HTTP 代理**：`scutil --proxy` 显示 `HTTPEnable: 1` / `HTTPSEnable: 1`。
  断网时代理返回 `HTTP 503`（而非 DNS/连接失败），所以异常类型是 `InvalidProxyStatus`。
  ⚠️ **这不改变结论**：根因是"任何重连异常都会被 `on_error` 抛出并杀死 task"，
  与异常的具体类型无关。但 **.51 现网若不走代理，暴露出的异常类型会不同**，
  复现时不要按 `503` 去找。

### 修法（一行，⛔ 留给另一条 opener）

在 `_prepare_client` 里补一个 `error` 监听器，让 pyee 走"有监听器 ⇒ 分发不抛"的分支，
`ws.py:153` 的 `_schedule_reconnect()` 便能正常执行。同时把 `max_reconnect_attempts`
改成 `-1`。两项都要有断线重连的自动化测试覆盖，⛔ 不许只靠手工复跑。
