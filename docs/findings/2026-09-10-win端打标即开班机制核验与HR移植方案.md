## 〇、先记一条读法纪律（本次踩坑的根治）

🔴 **「它解决的问题 / 为什么做这件事 / 成因 / 背景」这类小节一律是历史，⛔ 不得当现状引用。**
现状只认三处：**函数体、调度配置、测试**。
本次实证：起草者引 `工具-跟进闸查询.py` 开头「回件到达时机器人自动追§一行、拆件回灌由人写队列行，
唯独没有任何东西去改 README 那一格」判定「win 端拆件是人做的」——该句写于 2026-08-21，出自
「## 它解决的问题」，描述的是**造这个工具之前**的痛点；同一句在三处重复，全部是「为什么做」。

🔴 **同一份内容存在多个副本时，正本由「代码里解析该路径的那个函数」确定**，⛔ 不是文件系统里撞见的第一个。
此处＝`repo_paths.resolve_patrol_charter_path` ＋ `PATROL_CHARTER_RELATIVE_PATH`。
迁移后留在原地的旧件、应用面板里的旧注册项、被主动关掉的旧入口，都会以「看起来还在那儿」的方式骗人。

## 一、win 端真实机制（已核，非推测）

**链路：一次调用里做完三件事，零轮询。**
`followup_readme_bridge.mark_reply_arrived()` 在**同一把编辑锁内**：
1. README「发送状态」列写**第九态**：`📨 回件已到，待拆件 <UTC>（企微机器人自动标记，入信归档 \`<文件名>\`；
   **仍属在途、串行闸仍锁**，拆件回灌后须转闭环四态之一）　━━━　原状态 ━━━　<原状态>`
   —— **原状态原样接在后面**（可溯源）；第九态**仍属在途、串行闸仍锁**，是在「已推送」与「已闭环」之间**新插的一态**
2. `patrol_signal.raise_signal()` 落信号（JSON，`pending[]`，每条含 `letter_number` / `archived_filename` / `at`）
3. `patrol_dispatch.dispatch_headless_patrol()` **直接起无头会话**，不等任何定时器

**起活方式（已核 argv）**：`claude -p --output-format text --dangerously-skip-permissions`，
cwd＝仓库根，**prompt 走 stdin**（事件驱动前言 ＋ 章程全文），stdout/stderr → `reports/patrol-headless-logs/<UTC戳>.log`，
**非阻塞 Popen，不等子进程收工**。

**四条设计取舍（建议照搬）**：
1. **章程正本在仓库内，代码里不留副本**；运行时整段读出拼进 prompt。单测 `test_事件驱动前言不改写章程原文`
   断言章程原文必须逐字出现在 prompt 结尾、且其前必须有前言
2. **并发守卫用「pid 是否还活着」，不用「锁文件是否存在」**。锁文件记 `{pid, started_at, log}`；
   **判活查询本身异常时按「不存活」处理**——代价不对称：误判不存活＝多起一个（编辑锁兜住），
   误判存活＝该做的事没人做、信号原地卡死。坏锁（JSON 损坏）按陈旧锁处理照常起活
3. **fail-open 只对「起没起来」负责，从不读写信号文件**。四类失败（章程读不到／日志建不了／`Popen` 抛／兜底 except）
   全部只记 `ACTION_FAILED` ＋日志、**绝不向上抛**，信号原样留着，下一条真实回件会再触发。
   审计 `patrol_headless_dispatch_{started|skipped_busy|failed}`，`automation_level="L1"`；**留痕失败本身也被吞**
4. **非阻塞**：别把「标个状态」的延迟系在「干完一整套人工判断量级的活」上

**无头会话做什么（章程 §三）**：拿锁（`--who`）→ 升格前并入审核 → 回灌结论并 `append-row` 派生新行（⛔ 禁手写整行）
→ 口径点台账转态（`已签认` 强制 `--evidence`，缺则**退出码 3 拒绝**；**无任何超期自动签认路径**）
→ 重读比对 → release 六项结构校验 → 反查核验 → 登 §二 待 commit 批次。
**§〇 红线**：对外发送／建造／新裁决／design 审／L2 门禁／全景重组**一律不进池**；凡需**新下判断**转 §四 交人。
**§〇ter 信号探测**：`[NO-SIGNAL]` 即结束；`[SIGNAL]` 走全流程；**清信号在 §二 落批之后**（`--clear --before <检查点>`，
只清检查点之前的，保住起活期间新到的）；探测脚本出错／缺失／输出不认识一律**按 `[SIGNAL]` 处理**（宁多勿漏）。
另有一条只在调用侧前言、不写进章程正文的规则：走完一轮后**再探一次**，仍是 `[SIGNAL]` 就再走一轮，直到 `[NO-SIGNAL]`。

**运行器层**：Windows 计划任务（`ZhuopinAibotDevListener` 登录＋开机常驻等 5 项），以 `wscript.exe` 跑
`run-*-hidden.vbs`，工作目录在 worktree `wecom-service-home` 内 ＝「跑在 worktree 里的常驻服务」。
**macOS 对应面是 launchd**：`RunAtLoad`+`KeepAlive` ↔「登录＋开机常驻」，`StartInterval` ↔ `PT1H`。

## 二、映射到 HR：已有什么、缺什么

| 环节 | win 端 | HR 侧现状 | 判定 |
|---|---|---|---|
| 入信归档 | `archive_inbound_message` ＋防损坏校验 | `archive.py` ＋ `compute_archive_path` ＋幂等 | ✅ 已有 |
| 自动入队 | markdown 队列 ＋ 编辑锁 ＋ `append-row` ＋ hook | `enqueue_task` 写 `liaison_task` 表 ＋ FK ＋三态 CHECK ＋转移触发器 | ✅ 已有（载体不同，⛔ 不换） |
| **回件→跟进信 的桥** | `followup_readme_bridge`，靠**串行原则**取该收信人最近一封在途 | ⛔ **完全没有**——入站只知道「有人发了消息」 | 🔴 **缺口 0（前提）** |
| **README 第九态** | `📨 回件已到，待拆件`，仍在途、闸仍锁 | ⛔ 无。台账只有八态，`docs/跟进信/README-跟进信清单.md` | 🔴 缺口 1 |
| **打标即开班** | 同一次调用里落信号＋起无头会话，零轮询 | ⛔ 无 | 🔴 缺口 2 |
| **口径点台账** | `coverage_point_ledger`，`已签认` 必须 `--evidence`，无超期自动签认 | ⛔ 无 | 🔴 缺口 3 |
| **常驻运行器** | Windows 计划任务 5 项 | launchd 已装**值守服务**一项；拆件侧无 | 🟡 半有 |
| 拆件本身 | 无头会话按章程做 | ⛔ 无 | 随缺口 2 |

🔴 **载体取舍（照抄会翻车的地方）**：win 用「工具＋hook」在**入口**强制约束（绕开入口就没约束），
我们用「DB CHECK/触发器」在**引擎**强制（内容 grep 不到、git diff 不了）。两者各有失效面，⛔ 不存在谁天然更强。
**该移植的是流程与红线，⛔ 不是载体**——`liaison_task` 保持 DB，`docs/跟进信/README-跟进信清单.md` 保持 markdown
（它与 win 的 README 同为 markdown 表，第九态可直接照搬，且 `followup.py::compute_backfilled_ledger`
已有「按编号定位行 + 改状态列 + 去括注」的现成代码可复用）。

## 三、HR 侧独有的两条风险（win 端没有，⛔ 照搬会踩）

1. 🔴 **无头拆件会话与值守服务同机同仓**。win 端跑在 worktree `wecom-service-home` 里；
   我们的值守服务由 launchd 常驻在**主工作区**、正持有 `data/liaison.db`。
   ⇒ 拆件会话**必须在 worktree 内跑**，或写死「只碰 `docs/`、⛔ 不碰 `data/`」，否则抢库。
2. 🔴 **`--dangerously-skip-permissions` ＝ 该会话没有工具确认闸**。win 端靠章程 §〇 红线在**提示词层**兜，
   不是权限层。我们照搬时爆炸半径要自己权衡：HR 侧红线至少要含**对外发送**（`send-followup` ⛔ 不进池）、
   **建造**、**新裁决**、**改 spec/design**、**碰 `data/` 与 `.env`**。

## 四、分期（建议）

- **P0 桥＋第九态**（缺口 0＋1）：入站消息落库后，按串行原则定位该发送人在途的那封跟进信，
  在 `README-跟进信清单.md` 写第九态（原状态原样接后）。复用 `followup.py` 的行定位代码。
  ⚠️ 判据先定：**名单内且有在途信** ⇒ 标；**无在途信** ⇒ ⛔ 不标、只归档（这是我们比 win 多出的分支，
  因为我们的入站不只承接回件，还承接岗位需求）
- **P1 信号＋打标即开班**（缺口 2）：`patrol_signal` 等价物 ＋ 非阻塞起活 ＋ pid 判活并发守卫 ＋ fail-open 四分支 ＋ 审计
- **P2 章程**：HR 版拆件章程正本落 `.claude/skills/` 或 `docs/`，由单点常量解析；⛔ 代码里不留副本
- **P3 口径点台账**（缺口 3）：`已签认` 必须带 `--evidence`、⛔ 无超期自动签认
- ⛔ **不做**：不把队列换成 markdown、不引入编辑锁与 hook（我们已有 DB 约束）

## 五、验收纪律（比代码更重要）

🔴 **起活类机制的验收，必须有一次真实起活的实测记录，⛔ 单测不算。**
win 端 `tests/test_patrol_dispatch.py` 文首逐字：「真实 `Popen`／`tasklist` 一律不在单测里调用」，
真实起活验证登记在收工报告的手工实测记录里。我们移植时会很想拿「单测全绿」当验收标准——⛔ 别。
macOS 判活对应 `kill -0 <pid>` 或 `ps -p <pid>`，同样要把「查询失败」归到**不存活**一侧。
