## 3. TD-22 的实际报错原文

构造 `msgid = "CAQQ_xh7dGVzdA_1"`（base64url 形状，含两个 `_`）+ 一份 xlsx 附件：

```
ArchivePathError: msgid 含 '_'，会与 msgid/文件名分隔符 '__' 的边界混淆，
制造归档路径碰撞（4.1「归档覆盖」）；⛔ 不清洗，直接拒绝
```

**后果的完整形状（本轮新验的部分）**：异常抛在 `effect_archive_message` **之前**，
所以——材料没落盘、**台账一行都没写**、待办没生成。连"收到过这条消息"都无从查证，
**整条消息连同材料一起丢失**，只能靠上游重投。

**而症状是困惑而不是崩溃**：`compute_archive_path` 只在 `attachment is not None` 分支
下才被调用，所以同一个含 `_` 的 `msgid`，**纯文本消息照常归档 + 入队**（已用一条用例
钉住）。8.6 当天看到的会是：

> 「机器人明明在正常收消息、待办也在生成，偏偏一发文件就没反应。」

⛔ 排障时不要从"机器人是不是掉线了"入手。

## 4. 发现的问题

### 4.1 ⚠️ opener 与 spec 口径冲突：名单外的消息到底归不归档

- **0909AP opener 正文**写的是「名单外发送人 ＋ 带附件 ⇒ ⛔ 不归档、⛔ 不入队」；
- **spec 与 `inbound.py` 模块 docstring 的逐字原文**是：名单外的消息「SHALL 仍然归档
  （以便事后可查'谁在什么时候发过什么'）」，现有实现与 `test_inbound_routing.py`
  也都是这么做的。

**本轮取 spec**（保守方向：断言现网真实行为，⛔ 不让一条新测试去替 spec 改口径）。
两条真正的红线——**⛔ 不入队**、**只走礼貌回复**——都已断言。

> **待 Shao Peishen 裁定**：若「名单外不归档」才是真实意图，那是**合规口径的变更**
> （涉及对非受理对象的个人信息留存范围），⛔ 本泳道不自行改动。

> 🔴 **口径已裁定（Shao Peishen 2026-09-10 答 `2a`）：维持现状——名单外发送人的消息**
> **仍然归档。** spec 与 `inbound.py` docstring 的逐字原文（「SHALL 仍然归档，以便事后可查
> '谁在什么时候发过什么'」）为准，`0909AP` opener 里「名单外 ⇒ ⛔ 不归档」那句作废。
> ⇒ **本轮测试即最终形态，⛔ 不改 spec、⛔ 不改 `inbound.py`、⛔ 不另起泳道。**
> 已知代价（他已知悉并接受）：对非受理对象保留其消息与材料。
> 两条红线不变且已被断言钉住：名单外 ⛔ 不入队、只走礼貌回复分支。

### 4.2 🔴 新缺口：0 字节附件一路走通，全链路零症状（建议登记 TD）

> **本条按守住条款只登记、⛔ 未修**。已写成 `test_a_zero_byte_attachment_is_archived_and_enqueued_with_no_symptom` 钉住当前行为，请看护者转交进 `docs/tech-debt.md`。

一份 **0 字节**的附件会**完整走通**：落盘成功 → 台账写入 → 待办生成 →
`consistency.py` 的核对器报**空清单**。核对器核的是「台账说的长度/摘要与盘上一致吗」，
而 `byte_length=0` 与 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`
（空串的 SHA-256）**完美自洽**——这正是它无症状的原因。

**为什么是缺口**：`b""` 有两个来源，系统分不开——
1. 用户真的发了个空文件（罕见但合法，⛔ 不该拒收）；
2. **第 7 章通道层下载附件失败／拿到空响应**（真实，且 8.6 会发生）。

第 2 种情况下 Shao Peishen 的队列里会出现一条"收到材料"的待办，点开是个空文件，
**全链路没有任何一处报错或告警**。

**正确的修法在通道层，不在归档层**：aibot 协议下发的媒体项带声明长度，
第 7 章下载完应核对「实际字节数 == 协议声明字节数」，不符即当作下载失败重试／告警。
⛔ 不要改成"归档层拒收 0 字节"——那会误伤第 1 种情况。

### 4.3 ℹ️ 已知且刻意的中间态（⛔ 不是 bug，写下来防误判）

同一 `msgid` 第二次投递却带了**不同文件名** ⇒ 落点不同 ⇒ 盘上多出一份材料，
台账那一行仍指向第一份，于是出现**台账没有引用的孤儿文件**。
`consistency.py` 只核对「台账说有的、盘上是不是真有」一个方向，
反方向是 design D3 允许的、可由重跑收敛的中间态，报出来只会在崩溃恢复期刷假警报。

真实企微重投同一 `msgid` 时文件名不会变，概率极低。若 8.6 真在归档目录里看到
"多出来的一份"，正确处置是**对照台账确认哪份是权威的**，⛔ 不要以为归档坏了。

## 5. 🔴 8.6 当天该盯什么

### 链路一 · 名单内带附件（主链路）

**盯**：`data/liaison/archive/<userid>/<yyyymmdd>/` 下有没有出现
`<msgid>__<原文件名>` 这样的文件，且待办队列里有对应的一条。

- **落盘有、待办没有** ⇒ 归档提交后、入队前进程被杀。⛔ **不要手工补待办**，
  重投同一条消息即可（已验：归档幂等命中时仍会补上入队）。
- **待办有、落盘没有** ⇒ 🔴 这是 design D3 明令禁止的方向（"台账说材料收到了，
  材料却不在"）。**立即停止回灌**并留现场。
- **最快自检**：收完一批后跑一次台账↔材料核对器，应当返回**空清单**。
  ⚠️ 它查不出 §4.2 的 0 字节问题，见链路三。

### 链路二 · 🔴 TD-22（最可能当天爆的一条）

**盯**：日志里有没有 `ArchivePathError` + `msgid 含 '_'`。

**识别特征**：**文字消息一切正常、待办照常生成，只有带附件的消息全军覆没**。
因为"文档回灌只能走私信"，这等于**回灌功能整体不可用**。

- ⛔ **不要**当场把 `msgid` 里的 `_` 清洗掉让它通过——那会把「归档覆盖」的缝隙
  重新打开（见 `_validated_key` docstring 的单射编码推导）。
- 正确动作是**改 D4 的路径形态**：换一个不会出现在合法 `msgid` 里的分隔符，
  或把 `msgid` 单独放一段路径。这是 design 层变更，当天不要临时改。
- **当天的临时处置**：记录受影响的 `msgid` 清单，请 AI 专员改用**文字消息**
  先把内容发进来（那一支不受影响），附件延后。

### 链路三 · 0 字节 / 内容不对的材料（§4.2 的缺口）

**盯**：归档目录里有没有 **0 字节文件**，以及待办点开是不是空的。

```
find data/liaison/archive -type f -size 0
```

核对器**不会**报这个。当天只能靠这条 `find` 或人工抽查。
出现 ⇒ 是通道层下载失败，⛔ 不是用户发错了（先按下载失败处理，请对方重发一次确认）。

### 附：一并留意的三件小事

- **中文长文件名**被按字节截断是**正常**的（255 字节上限），扩展名会保住 —— 已验。
- 归档目录出现**多出来的一份**同 `msgid` 文件，见 §4.3，⛔ 不是归档坏了。
- 看到 `AttachmentIntegrityError` ⇒ 同一条协议消息带来了两份**不同**字节，
  是协议层的怪事。⛔ 不要靠删旧文件来"修"。
