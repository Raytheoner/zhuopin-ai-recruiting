## 1. 现象

`test` job（windows-latest + Python 3.14.6）三个用例失败，本地 macOS 同版本 venv
连跑 5 次 81 个全绿、零波动。

| 用例 | 报错 |
|---|---|
| `test_graph_nodes.py::test_build_intake_graph_runs_end_to_end` | `cannot start a transaction within a transaction`（原始）→ `cannot rollback - no transaction is active`（掩盖） |
| `test_web_api.py::test_app_works_when_mounted_at_arbitrary_subpath` | `cannot commit - no transaction is active` |
| `test_web_api.py::test_second_turn_prompt_contains_first_turn_message_and_known_fields` | 同上 |

## 2. 根因

`app/graph/build.py` 结尾：

```python
checkpointer = SqliteSaver(conn)      # ← 与 effect 层共用同一个 sqlite3.Connection
return graph.compile(checkpointer=checkpointer)
```

注释写明这是刻意的（"reuses the connection this function already received rather
than opening a second one to the same file"）。问题在于**这个连接上有两个独立的
事务管理者**：

- **effect 层**：`idempotency.py:53` 的 `conn.commit()`、第 45 行的 `conn.rollback()`
- **LangGraph 的 SqliteSaver**：每个 superstep 之间写 checkpoint，自行 commit

于是 Python `sqlite3` 模块内部记的"事务是否打开"与 SQLite 实际状态脱节：

```
_persist_node → effect_persist_draft → INSERT      （Python 隐式 BEGIN）
      ↓
LangGraph 写 checkpoint → SqliteSaver commit       （事务被别人关掉了）
      ↓
idempotency.py:53  conn.commit()                   → cannot commit - no transaction is active
```

deliver 那条路径反过来：checkpointer 已经 BEGIN 而 Python 不知情，`web_channel.py:31`
的 INSERT 触发 Python 再发一次 BEGIN → `cannot start a transaction within a transaction`；
随后 `idempotency.py:45` 的兜底 `rollback()` 又落在已经没有事务的连接上，**把原始异常
掩盖成了一个误导性的 rollback 错误**。

## 3. 已被证伪的假设（重要，别按它立项）

最初的分析认为是「LangGraph 把 `effect_persist_draft` 与 `effect_deliver_message`
并发派发到线程池，两个线程同时写同一连接」。**这个假设不成立**，三条独立证据：

1. **图是严格线性链**：`build.py:63-65` 是 `compute → persist → deliver → END`，
   无分叉，就没有同一 superstep 内的并发派发
2. **traceback 里是直接调用**：`_runner.py:167 tick` → `run_with_retry` → `task.proc.invoke`，
   中间没有任何 `concurrent.futures` 帧。并发派发会有
3. **本地 5/5 零波动**：时序竞态不会呈现这种确定性

区别是实质性的：竞态的修法是加锁，事务归属冲突加锁**修不好**——两个管理者在
同一个线程里也照样互相踩。

### 3.1 订正（2026-08-13，spec-to-plan 阶段新发现，不推翻上面的结论）

写 `fix-sqlite-transaction-ownership` 第 1 章实现计划时，在本机（macOS，非 CI）
用 `venv/bin/python -m pytest -q` 反复跑全量测试套件（15 次命中 2 次），拿到过
一次**完整**的本地失败 traceback，其中包含：

```
File ".../langgraph/pregel/_executor.py", line 117, in __exit__
    task.result()
File ".../concurrent/futures/thread.py", line 86, in run
    result = ctx.run(self.task)
File ".../langgraph/checkpoint/sqlite/__init__.py", line 447, in put_writes
    with self.cursor() as cur:
File ".../langgraph/checkpoint/sqlite/__init__.py", line 175, in cursor
    self.conn.commit()
sqlite3.OperationalError: cannot commit - no transaction is active
```

`put_writes()` 确实是从 `concurrent.futures.thread` 的 worker 里被调用的——**上面
反证 2 的表述不准确**：LangGraph 的 Pregel 执行器（`langgraph/pregel/_executor.py`
的 `BackgroundExecutor`）内部本来就用线程池派发节点/checkpoint 相关调用，哪怕图
严格线性、没有 fan-out。当时的反证 2 只看了某一次具体 CI 失败自己的调用栈——单个
线程自己的 traceback 天然看不到另一个线程的存在，不足以证明"从不存在
`concurrent.futures` 帧"。反证 3（"本地 5/5 零波动"）同样是取样不足：15 次里能
中 2 次，说明当时只是跑的次数不够多，不是问题在本地不存在。

**这不推翻最终结论**：反证 1（图无分叉，没有应用层节点级别的并发派发）依然成立，
"并发写冲突"指的是应用代码层面互相踩，这件事确实没有发生。已核实
`SqliteSaver` 自己用 `threading.Lock` 序列化了它对连接的 `cursor()`/`commit()`
调用（`langgraph/checkpoint/sqlite/__init__.py:82,168`），所以哪怕它被线程池
调度，也不会自己跟自己竞争。真正的问题始终是"一个连接上有两个互不知情的
提交者"，不是"谁跟谁抢锁"——**竞态的修法是加锁，这条修不好**这句话依然成立，
只是现在多了一层机制解释：跨线程调度是"为什么本地默认测不出来、CI 上偶发、
且两次代码不变的 CI 运行会命中不同用例"的更完整原因，而不只是"单线程内调用
顺序的偶然性"。

方向 A（checkpointer 独立连接）修复后，effect 层不再从任何线程触碰 checkpointer
的连接，跨组件竞争不再可能——这条订正不需要新增修复步骤，只是把这里的证据
表述改准确。

## 4. 关于"为什么只在 Windows 上炸"——这个问题不必追下去

版本已采到：**本地 macOS 3.53.3，CI Windows 3.50.4。**

⚠️ **这个对比得不出结论，因为两个变量同时变了**（平台 macOS→Windows、SQLite
3.53.3→3.50.4）。原先"版本接近就判定是平台差异"的判据是拍脑袋定的，不成立——
版本号数值接近不等于行为接近，3.50 到 3.53 隔了三个 minor、约一年的改动。

**但更重要的是：这个归因不影响该修什么。** 第 2 节的机制——一个连接上两个事务
管理者——是**平台无关的逻辑缺陷**，任何平台都成立。平台与版本只决定它**是否被
触发**，不决定它**是否存在**。macOS 上没炸只是恰好没踩到那个交错顺序。

真正决定优先级的问题只有一个：**生产服务器会不会踩。** 而这个问题有直接答案——
`.51` 就是 Windows，CI 的 Windows 已经稳定复现两次。

可以进一步确认的一点（一条命令）：`.51` 上 Python 3.14 大概率与 CI 用的是同一个
python.org 官方构建，因而**很可能捆绑同一个 SQLite 3.50.4**。若确认相同，则
"服务器会精确复现" 从推测变成事实，优先级直接拉满。

**不建议**为了归因去本地装 3.50.4 反向复现——投入不小，而结论不改变修法。

**实测（2026-08-18）**：`.51` 为 Python 3.14.5（MSC v.1944 64bit）/ SQLite **3.50.4**，
与 CI（windows-latest，3.50.4）**完全一致**。上面"很可能捆绑同一个 SQLite"的推测就此
坐实——生产环境会精确复现，不是"M2 前要解决"，而是修复前的 M1 演示期就已经在踩。
现网实际踩到的证据见第 8 节。


## 5. 影响面

直接命中 `CLAUDE.md` 工程铁律第 1、2 条。幂等键机制依赖 `effect_log` 与业务写入
在**同一个事务里原子提交**；事务被第三方随机切断后：

- `effect_log` 可能已提交而业务写入被回滚（或反之）→ 幂等键失去意义
- `idempotency.py` 的异常兜底路径本身会抛二次异常，**掩盖原始错误**，线上排查困难

按部署约束第 5 条，M2 起处理真实简历前必须解决。

## 6. 候选方向（未评估，留给设计阶段）

1. **给 checkpointer 单开一个连接**——最直接，回到 `SqliteSaver.from_conn_string()`
   并用 `with` 正确持有。代价：两个连接写同一 SQLite 文件，要处理锁竞争
2. **让 effect 层不自己管事务**——把 commit/rollback 收敛到一个统一的事务边界
3. **M2 迁 Postgres 时一并解决**——但那之前的 M1 演示仍会踩

不要在环境线顺手改。走 `openspec-propose` 正规立项，spec 里应包含一条能在
**任意平台**复现该冲突的回归测试——本地测不出来正是它活到今天的原因。

发生的既成损伤，不需要发版处置。

**损伤清单（2 次，均在修复合入之前）**

| thread | 岗位 / 日期 | `effect_deliver_message` | `outbox` | 丢失的那一轮 |
|---|---|---|---|---|
| `1cabfb91-74a4-46e2-8679-ded1939759cb` | 采购工程师，2026-08-12 | 7 条 | 6 行 | 09:49:09（round 3） |
| `41909b40-3e47-499a-88ed-69ac804948aa` | 采购，2026-08-10 | 8 条 | 7 行 | 07:16:00（round 4） |

也是下面铁律补强的直接来源。

**可观测后果：AI 在为一次它以为自己犯的重复道歉。** 两个 thread 丢失轮的**下一条**
`outbox` 都以同一句开头：

- `1cabfb91` 09:52:16：「抱歉，刚才的问题重复了。我们继续确认岗位信息：该岗位是否
