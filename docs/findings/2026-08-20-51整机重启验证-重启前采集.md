## 二、四条发现

### A【阻断，已清除】任务计划程序历史通道是关闭的

    Microsoft-Windows-TaskScheduler/Operational
      重启前  IsEnabled: False   RecordCount: (空)   MaxSizeMB: 10

opener 要求"查任务计划程序的历史记录，不要只看进程在不在"。该通道禁用时，重启后
100/129/102 事件根本不会产生，那一梯度的证据直接缺失，而且**不报错、只查出一片空**。

处置（本轮服务器侧唯一改动，可逆、不重启任何服务）：

```
ssh zp51 'wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true'
```

    验证后  IsEnabled: True   MaxSizeMB: 10   RecordCount: 0     回滚 /e:false

另有两个非 Running 的根级任务：`ECUSalesDashboard`（Ready，LastRun `1999/11/30`，

### C【风险，也是收益】8 个服务的开机自启从来没被证明过

上次开机 2026-05-26，而 8 个服务的 `LastRunTime` **全部晚于该时刻**（最早的
`SupplyChainWebServer` 是 6-02），说明当前这批运行实例都是开机之后起来的，没有任何一个
的 Boot 触发器在真实重启里被验证过。

- 收益：一次重启同时验掉 8 个服务的自启
- 风险：某个服务自启是坏的，就是那个部门直接下线，且**在有人反馈之前不会有告警**

缓解：8 个任务逐条查过，账户全 `SYSTEM`、触发全 Boot、`Enabled` 全 True，配置层面没踩
07 文档第三节第 14 条那个 `AtLogOn` + 交互式账户的坑。配置正确 ≠ 一定能起，但至少不是
明知有坑还去撞。

### D【风险】有挂起的组件服务操作，停机时长不可预估

    CBS RebootPending             : True
    PendingFileRenameOperations   : True
    WindowsUpdate RebootRequired  : False
    wuauserv 启动类型              : Manual（不会自动装更新）
    最近补丁                       : KB4589208 @ 2021-11-10

CBS 挂起 + 文件改名挂起，意味着关机/开机时会执行一批组件服务操作。叠加 85 天未重启，
停机时长会明显长于普通重启，且极小概率触发回滚。窗口要留余量，不能按"两分钟就回来"估。

## 三、为什么最终没有重启

**放行时刻服务器侧是周四上午上班高峰。**

    开发机 Mac   2026-08-19 23:31 EDT (-0400)
    服务器 .51   2026-08-20 11:31 China Standard Time（周四）

两地差 12 小时。Mac 侧是深夜、看着像天然低峰；服务器侧是周四 11:31，报关、供应链、
财务 Fi2、清单 B、SC2、指挥中心、统一门户网关这 7 个业务系统正在被用。叠加发现 D 的
不可预估停机时长，不满足 opener 前置 2 的「低峰窗口」。

### 后续处置：开发机已改为 +0800

当日随即把开发机时区改为 `Asia/Shanghai`（`+0800`），与 `.51` 的 China Standard Time
对齐并实测确认（两边同为 `2026-08-20 11:54 周四`）。误判来源消除，附带收益是 git commit
时间戳也变成 `+0800`，可与服务器日志、任务计划历史直接对齐。

**但这不改变本次的判断**——对齐消掉的是"看错钟"，不是"现在是高峰"这个事实本身。

已沉淀为 07 文档第三节第 16 条：**涉及停机窗口的决定，仍先 `ssh zp51` 取服务器本地时间
与星期，再谈低峰。** 时区对齐是当前这台机器的状态，不是系统性保证——换机器、出差改时区、
别人代跑都会让它重新失效，而失效时没有任何症状。

### 推荐窗口

两机时区已对齐，以下一律是两边共同的钟点（`+0800`）：

| | 窗口 | 说明 |
|---|---|---|
| **首选** | 2026-08-22（周六）08:00 | 即使 7 个服务里有一个没自动回来，也有整天时间在业务受影响前处理 |
| 次选 | 2026-08-21（周五）07:00 | 上班前，但若需回滚余量偏紧 |
| 可接受 | 2026-08-20（周四）20:00 之后 | 当晚即可，代价是出问题时次日上班前才有人跟进 |

## 四、窗口到了之后的执行序列

历史通道（发现 A）已开，不用再做。

1. `ssh zp51 'shutdown /r /t 60 /c "OP-0820-9 计划任务自启验证" /d p:2:4'`
2. 轮询 ssh 直到重连成功，记录**实际停机时长**（对照发现 D 的预估）
3. **梯度一**：`Get-WinEvent -LogName Microsoft-Windows-TaskScheduler/Operational` 查
   `ZhuopinRecruitAgent` 的 100（任务启动）/ 129（创建进程）/ 102（任务完成）事件；
   并核 `Get-ScheduledTaskInfo` 的 `LastRunTime` 是否等于本次开机时刻。
   **只看进程在不在不算数。**
4. **梯度二**：服务器本机与开发机 Mac 两侧 `curl http://192.168.100.51:8095/hr/recruit-agent/`
   （单侧不算数，见 07 文档第三节第 11 条）
5. **耦合点**：`app.log` 仍在 `C:\apps\zhuopin-recruit-agent\logs\`，`Length > 126`，
   `LastWriteTime` 晚于开机时刻，且 `C:\Windows\System32\logs\` 下没有同名文件
6. **附带**：另外 7 个服务是否全部自动回来
7. 进程 PID 必须区别于重启前的 `4148` / `4764`
