## 观察项一：漏消息告警是否误报

**告警文本**：`tools/liaison/alerts.py:20` `ALERT_RESEND_SENTENCE = "该时段消息可能未收到、请重发"`（中断窗口关闭时发出）。

**取数**

```bash
grep -c '连接中断' data/liaison/logs/liaison.log                                  # → 23（全量）
grep -c '该时段消息可能未收到' data/liaison/logs/launchd.err.log                    # → 21
sqlite3 -header "file:data/liaison.db?mode=ro" \
  "SELECT * FROM liaison_outage_window WHERE started_at >= '2026-09-17T12:29' \
   AND started_at < '2026-09-25' ORDER BY started_at;"                            # → 5 行
```

**窗内 5 条告警逐条判定**（`liaison.log` 行号为该文件内行号）

| # | 证据行 | 中断区间（CST） | 时长 | `detected_by` | 窗内是否有消息落库 | 判定 |
|---|---|---|---|---|---|---|
| 1 | `liaison.log:205,210` | 09-17 13:27:31 → 13:27:34 | 2 秒 | `startup_gap` | 无 | **噪声级**（命中开窗预登记的「<10 秒瞬时抖动仍告警」判据）⇒ 误报面 |
| 2 | `liaison.log:235,240` | 09-17 13:30:34 → 13:30:43 | 9 秒 | `startup_gap` | 无 | **噪声级** ⇒ 误报面 |
| 3 | `liaison.log:249` | 09-17 14:42:29 → 14:42:43 | 14 秒 | `startup_gap` | 无 | 真中断窗口（>10 秒），无漏收证据 |
| 4 | `liaison.log:258` | 09-17 21:35:01 → 21:35:09 | 8 秒 | `startup_gap` | 无 | **噪声级** ⇒ 误报面 |
| 5 | `liaison.log:279` | 09-22 10:45:30 → 10:48:15 | 2 分 44 秒 | `startup_gap` | 无 | 真中断窗口（窗内最长） |

**对照查询**（11 条消息**无一**落在任何中断窗口内）：

```sql
SELECT m.received_at, m.msgid, m.thread_id,
       (SELECT COUNT(*) FROM liaison_outage_window w
         WHERE m.received_at >= w.started_at AND m.received_at <= w.recovered_at) AS in_window
  FROM liaison_message m ORDER BY m.received_at;   -- 11 行，in_window 全为 0
```

**结论**

1. 窗内 5 条告警**全部**由 `startup_gap` 产生（服务重启后的启动期补记），**没有一条**来自 `disconnect_event` ⇒ **观察窗内没有发生过一次网络断线型中断**；这 5 条本质是「重启噪音」，不是「网络故障漏消息」。
2. 3/5（2 秒、9 秒、8 秒）时长 <10 秒，按**开窗时预登记的判据**属噪声级告警 ⇒ 记为**误报面**；2/5（14 秒、2 分 44 秒）为真中断窗口，告警对「这段时间可能收不到消息」的提示是成立的。
3. 这 5 条「窗内到底有没有消息被真漏掉」——**判不准**：服务侧只能证明「窗内没有消息落库」（11 条消息的 `in_window` 全为 0），证明不了「发送方那条消息被丢了」。要判准必须拿到发送侧记录（谁在 13:27:31–13:27:34 这类窗口内发过消息），而那属外部输入，本 session 取不到。
4. 累计量对基线的增量：`launchd.err.log` 该句 `15 → 21`（+6，含 09-16 14:20:35 假死告警 1 条与 09-30 08:04 重启 1 条，均**在窗外**）；`liaison_outage_window` 表 `17 → 23` 行（+6，其中窗内 5 行，另 1 行为 09-30 08:04）。
5. `tick.out.log` 29 轮 tick **全部**「告警 0」，但该计数属 dispatcher tick 的入队统计（入队对象是 `lanes-*` 批次与 `observation:2026-09-17-值守通道一周观察窗.md:2026-09-24`），**不是** liaison 连接告警计数 ⇒ 只作「观察窗到期提醒已入队并被通知」的佐证（`owner_notify_outbox` 第 42 行 `observation:…:2026-09-24` 已发，`liaison.log:2026-09-24 09:00:16` 有对应「本人通知已发」行）。

> **本次观察暴露的判据缺口（登记，⛔ 未改）**：开窗文件那条「误报」判据有两个并列分支，第二分支「告警触发时实际没有消息被漏收——可用 `liaison_message.received_at` 落在该窗口区间内核对，命中任何一条即说明确有消息经过、不算误报」在**服务侧不可判定**：`liaison_message` 只记「收到了什么」，永远看不到「用户发了但没到」的那条。⇒ 该分支只能靠发送侧记录闭合。属**改判据**范畴，超出本 session 授权（3a），只登记不动手。

## 观察项二：限流是否被触发

**机制**：`tools/liaison/notify/ratelimit.py` 的 `TokenBucket`（群 webhook 令牌桶，容量 20、按 20/60s 补充），只在群通知回推链路上生效。

**取数**

```bash
grep -n -i -E 'ratelimit|rate limit|限流|频控|backoff|退避|45009|重试' \
  data/liaison/logs/liaison.log            # → 0 行
grep -c -i -E 'ratelimit|rate limit|限流|频控|backoff|退避|45009' \
  data/liaison/logs/launchd.err.log        # → 1 行
grep -c -i '重试' data/liaison/logs/launchd.err.log   # → 0 行
```

那唯一 1 行是**时间戳误命中**，不是限流事件：

```
27707:[2026-09-14T10:45:28.845009+00:00] [AiBotSDK] [DEBUG] Received heartbeat ack
```

（`10:45:28.845009` 里含子串 `45009`。）排除后**窗内与全量均为 0 命中**。

**为什么必然为 0**（结构面，与开窗文件同口径）

```bash
grep -q '^HR_LIAISON_GROUP_WEBHOOK' .env || echo '无该行'   # → 无该行（只查键名存在性，未打印任何取值）
sqlite3 "file:data/liaison.db?mode=ro" "SELECT COUNT(*) FROM liaison_group_notify;"   # → 0
sqlite3 "file:data/liaison.db?mode=ro" \
  "SELECT COUNT(*) FROM liaison_task WHERE pushed_at IS NOT NULL;"                    # → 0（11 行全 pending）
```

**结论**：观察窗内**零命中**（这是事实，有上面的命令与输出行数作证）。至于限流机制本身是否正常——**判不准**：群 webhook 从未配置、回推链路 0 次真实投递，令牌桶在结构上不可能被触发。⛔ **不得**据此判定「限流机制已验证正常」（与 `docs/findings/2026-09-17-值守通道一周观察窗.md` 同一口径）。

## 观察项三：归档是否有重名冲突

**机制**：归档叶子路径为 `<msgid>__<安全文件名>`；`msgid` 是 `liaison_message` 主键，结构上两条不同消息不可能共享同一叶子前缀。

**取数**

```bash
find data/liaison/archive -type f | sed -E 's#.*/([^/]+)__.*#\1#' | sort | uniq -d   # → 空
find data/liaison/archive -type f -exec basename {} \; | sort | uniq -d              # → 空
sqlite3 "file:data/liaison.db?mode=ro" "SELECT COUNT(*) - COUNT(DISTINCT msgid) FROM liaison_message;"  # → 0
grep -n -E '重名|同名|覆盖|冲突|collision|overwrite' data/liaison/logs/liaison.log   # → 0 行
find data/liaison/archive -type f | wc -l                                            # → 10
```

**目录清单**（3 个 `thread_id` × 日期，10 份文件，叶子前缀全不同）

| thread_id | 日期 | 份数 |
|---|---|---|
| `ShaoPeiShen`（私信） | 20260917 | 1 |
| `TangLiPing`（私信） | 20260917 / 20260921 | 1 / 2 |
| `wrvDL_DAAAnkeGLkk1_bu2Ne1oQfc4BA`（群） | 20260917 / 20260920 / 20260924 | 2 / 2 / 2 |

**结论**

1. 观察窗内**零重名冲突**：归档文件数 `3（09-17 基线）→ 10`，10 个叶子前缀（`msgid`）去重后**无重复**；同日同目录同名文件 0 组；`liaison_message` 的 `COUNT(*) - COUNT(DISTINCT msgid) = 0`；日志里 `重名/同名/覆盖/冲突/collision/overwrite` **0 命中**。
2. ⚠️ **样本面**：这 10 份**全部**是 `<msgid>__正文.txt`，`attachments_json` 11 行全为 `[]` ⇒ 题面里「同名附件互撞」那一类生产 bug 场景**窗内无样本**。因此本项只判到「**结构面成立 ＋ 窗内零反例**」，**不能**判成「同名附件场景已实测通过」。
3. 相关但**不属本项判据**的一条窗内 ERROR（不计入上述三条）：`liaison.log:274` `2026-09-21 11:08:40 ERROR tools.liaison.__main__: 入站附件未落盘（…fail-closed；正文照常归档）`，对应 `msgid=459b735f…`（`TangLiPing` 私信 `msgtype=file`）——附件字段映射未定（TD-51）走 fail-closed，正文照常归档，故该 msgid 在归档树里只有 `__正文.txt`。归 TD-51，不属本次三项判据。
