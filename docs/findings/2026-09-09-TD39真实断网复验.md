## 三、第二段·自动断网（脚本全自动）

脚本 `/tmp/aj/outage.sh`，后台跑。三件事在关网**前**全部写死：独立兜底 `sleep 900`、
`trap restore EXIT INT TERM`、2 秒一次的采样循环（断网 245 秒内 CC 自己也没网，
⛔ 无法中途调整）。

```bash
#!/bin/bash
DEV=en1
REPO=/Users/paulshao/Projects/HumanResource
LOG=/tmp/aj/samples.log
( sleep 900; networksetup -setairportpower "$DEV" on ) >/dev/null 2>&1 &
disown
restore() { networksetup -setairportpower "$DEV" on; echo "$(date '+%T') RESTORE-TRAP" >> "$LOG"; }
trap restore EXIT INT TERM
sample() {
  echo "=== $(date '+%T') phase=$1 ===" >> "$LOG"
  cat "$REPO/data/liaison/liveness.json" >> "$LOG" 2>&1; echo >> "$LOG"
  sqlite3 "$REPO/data/liaison.db" \
    "select started_at,recovered_at,closed_by,alerted_at,detected_by from liaison_outage_window order by started_at;" >> "$LOG" 2>&1
  tail -4 /tmp/aj/stderr.txt >> "$LOG"
}
for i in $(seq 1 8);   do sample BEFORE;  sleep 2; done
echo "$(date '+%T') >>> WIFI OFF" >> "$LOG"
networksetup -setairportpower "$DEV" off
for i in $(seq 1 120); do sample OUTAGE;  sleep 2; done
echo "$(date '+%T') >>> WIFI ON" >> "$LOG"
networksetup -setairportpower "$DEV" on
for i in $(seq 1 120); do sample RECOVER; sleep 2; done
echo "$(date '+%T') >>> DONE" >> "$LOG"
```

**关键时刻**（`samples.log` 原文行）：

```
23:02:17 >>> WIFI OFF
23:06:22 >>> WIFI ON
23:10:26 >>> DONE
```

**断网时长 = 245.0 秒**（> 阈值 180 秒 ✅，对比 `0909AG` 的 91.77 秒）。
复网后观察 244 秒。全程 508 秒，`trap` 与独立兜底均未被用到（脚本正常走完）。

### ⑦ 🔴 恢复是哪一层做到的 —— 只有改法 1，看门狗未触发

三条判别 grep 的原始输出：

```
$ grep -c "值守通道连接报错，已交给 SDK 重连" /tmp/aj/stderr.txt
9

$ grep -n "存活戳已" /tmp/aj/stderr.txt
2:2026-09-09 22:59:00,917 WARNING  存活戳已 180 秒以上没有刷新（末次 2026-09-09T22:03:24.171999+08:00）…
4:2026-09-09 22:59:00,918 ERROR    存活戳已陈旧，但没有可停的事件循环把手…

$ grep -n "值守通道连接结束（第" /tmp/aj/stderr.txt
（无输出）

$ awk '/2026-09-09 23:0[2-6]/ && /存活戳/' /tmp/aj/stderr.txt | wc -l
0
```

判读：

- **改法 1 命中 9 次**，每次都是「不回抛、交给 SDK 重连」⇒ `_schedule_reconnect()` 得以执行
  ⇒ 退避链完整跑到第 10 次成功。**这一层被真实验证了。**
- **看门狗两条命中都在 22:59:00**，即本次断网**之前** 3 分 17 秒，是第二节记的
  **启动瞬间误触发**，与本次断网无关。**断网窗口 23:02:17–23:06:22 内看门狗零日志**
  （见上面第四条 `awk`，计数 0）。
- **外层 `run_forever` 零命中** ⇒ 从未接手。

**机理**（解释了看门狗为什么*按设计*就不该触发）：改法 1 生效后，每次重连失败都会触发
`error` 事件、刷新一次存活戳。SDK 退避上限是 30 秒 ⇒ 存活戳最大间隔 30 秒 ⇒
**永远达不到 180 秒阈值**。两层是"改法 1 修好则看门狗静默"的关系，不是并联触发。

⇒ 落在 opener 第四节的**第二种分叉**：「只有第 1 条命中、第 2 条没有 ⇒ SDK 自己的重连链
已修好，在阈值内自愈 ⇒ ④⑤⑥ 绿即算通过」。

🔴 **因此必须明写：N-0 兜底层（看门狗）本次未被触发，仍只有单测覆盖**
（`tools/liaison/tests/test_session_client_reconnect.py`）。⛔ 不许把本次实测记成
"两层都验过了"——那是编造未发生的证据。要真实触发看门狗，需要构造
"SDK 事件完全静默但 loop 还活着"的形态（`0909AG` 撞到的那种 task 已死场景），
**普通断网复现不出来**。
