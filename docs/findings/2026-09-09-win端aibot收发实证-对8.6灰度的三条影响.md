# win 端 aibot 收发方式实证 —— 对 8.6 灰度与第 4/6 章假设的三条影响

**来源**：Shao Peishen 2026-09-09 口述（win 端已跑通两个月的实际做法）＋ 本会话读 win 端源码核对：
`5-平台底座/wecom-aibot-service/aibot_service/delivery.py`、`scripts/push_followup_letter.py`、`aibot_service/dispatch.py`
（GitHub raw 只读，≤36 KB 可取）。

## 一、aibot **能主动发**，单聊与群聊走同一个方法，只差 chatid

`delivery.py` 的推送序列（逐字）：

```python
await connector.send_markdown(chatid, body)
await connector.send_file(chatid, media_id)
# 抄送部门群：
await connector.send_markdown(cc_group_chatid, f"{CC_PREFIX}{body}")
await connector.send_file(cc_group_chatid, mid)
```

`dispatch.py` 里 `KNOWN_RECIPIENT_USERIDS = {"姚祖怡": "YaoZuYi", ...}` 是**静态映射**，chatid 预先解析好、不在运行时发现。

🔴 **本会话此前说的「aibot 是被动应答形态、不能主动私信」是错的，已作废。**
**前置条件**（Shao Peishen 口述）：**AI 专员先私信 @ 一次机器人**，那个单聊 chatid 才存在／可用；之后我方就能主动往该 chatid 推。

## 二、群聊只承载文字，**文档回灌只能走私信**

- 群里 @ 机器人：**只能收文字平信**
- **文档（简历／JD／批改回件）回灌：只能专员私信机器人**

🔴 **对第 4 章的影响**：附件归档链路（`archive.py` / `attachments.py` / `compute_archive_path`）如果只在群消息上验证，**永远验不到真实附件**——它在群里根本不会到达。
🔴 **对 8.6 灰度的影响**：验收步骤必须**先加一步「专员私信一次机器人」**，否则「归档带附件」这条链路等于没验。
⚠️ 与 TD-22 直接相关：真实 `msgid` 的字符集要在**带附件的私信**上核，群里的纯文本消息核不出那个风险。

## 三、aibot 开机即在线（长连接监听），与 TD-19 呼应

win 端「只要开机就在线」＝ SDK 长连接监听形态跑得通 ⇒ 这条路本身没问题，
我们缺的只是把**真正的阻塞入口 `client.run()`** 接进 `session_client.run_forever`
（`connect` 是 `async def`，同步调用只返回协程对象、不建连——`make_sdk_connect` 正是据此拒启动）。

## 四、必须分清的一件事：「值守服务能发」≠「Cowork 能发」

- **值守服务**由 launchd 在 **macOS 原生环境**跑，用这台电脑的正常网络 ⇒ 能连 `qyapi.weixin.qq.com`，发送是它的事
- **Cowork 的 shell** 在隔离 VM 里：2026-09-09 实测 `qyapi.weixin.qq.com` **无 DNS 解析**；云容器经代理 `CONNECT` 得 **403**（不在 egress 白名单）
⇒ 服务起来之后发消息**不需要**我这边有网；只有「让 Cowork 代发」才需要把该域名加进会话 egress 白名单。

## 五、由此得出的 8.6 灰度正确顺序

1. 汤丽萍**私信一次**机器人（打开单聊 chatid，⛔ 少这一步文档链路不通）
2. 还 TD-19：把 `client.run()` 接进 `run_forever`，真实凭据端到端验建连与断线重连
3. 验三条链路：群里文字需求 → 入队；**私信文档 → 归档（含附件路径与 msgid 字符集，核 TD-22）**；群通知 → 回推
