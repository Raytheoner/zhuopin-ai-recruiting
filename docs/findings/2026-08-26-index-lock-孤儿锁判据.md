## 1. 现象

`OP-0826-A` 那一轮把 8 处改动全部改完（决策回填、opener 校验 hook、收口判据补强），
每次 `git commit` 都报：

```
fatal: Unable to create '/Users/paulshao/Projects/HumanResource/.git/index.lock': File exists.
```

opener 里内嵌的并发协议第 4 条写的是「等 5 秒重试最多 5 次，⛔ **绝不删除该锁**」。
执行方逐字照办：重试 5 次、全部失败、**停下不删**，把改动留在工作区并如实汇报。

**这是规则被正确执行的结果，不是执行失误。** 但代价是整轮产出零落地——
改动只活在工作区里，任何一次误 `git checkout` 或换机器都会全丢。

## 2. 「绝不删除」这条规则原本防的是什么

防的是**并行 session 互相破坏**：A session 正在 `git commit`（index.lock 存在的正常窗口
是毫秒到秒级），B session 看见锁就删，A 的提交当场被毁。这个风险是真的，规则本身没错。

规则错在**把「锁存在」等同于「有人正在用」**。锁文件是进程崩溃/被杀/容器消失后
**不会自动清理**的——持有者已经不在了，锁还在。这种锁叫孤儿锁，
它不代表任何人的提交，只是一具尸体。对孤儿锁执行「绝不删除」＝**永久阻塞本仓库的所有写操作**，
而且和真锁一样**没有任何报错以外的症状**：git 只说 `File exists`，不告诉你持有者死没死。

## 3. 放宽后的判据（三项同时成立才可删）

| # | 判据 | 怎么查 | 为什么 |
|---|---|---|---|
| 1 | 文件 **0 字节** | `ls -l .git/index.lock` | git 写 index 时会往 lock 文件里写内容再 rename。0 字节＝创建了但一个字节都没写，基本排除"正写到一半" |
| 2 | **mtime 距今 > 10 分钟** | `ls -l` / `stat -f %m` | 正常提交持锁是毫秒~秒级。10 分钟是给大仓库 `git add` 的极宽裕余量 |
| 3 | **无 git 进程**，且 `.git` 下**无写 FD** | `pgrep -x git`；`lsof +D .git` 看 FD 模式 | 直接证明没有活着的持有者。**只读 FD 不算**——只读打开不可能是在写 index |

**三项少一项都按"别人在用"处理**，继续等或停下问人。判据是保守的：宁可多等，不可误删。

### 3.1 判据 3 的两个坑

**坑一：`pgrep -f git` 会大量误报。** 本次实测宿主机上 `pgrep -f git` 命中 **9 个进程**，
全部是微信的 WebView 子进程——命令行里带 `--disable-features=...,DigitalGoodsApi,...`，
`Di·git·alGoodsApi` 里含 `git` 三个字母。同一时刻 `pgrep -x git` 返回**空**（exit 1）。

> ⛔ 查 git 进程用 `pgrep -x git`（精确匹配进程名），不要用 `pgrep -f git`（匹配整条命令行）。
> 用 `-f` 会让判据 3 恒不成立，判据形同虚设。

**坑二：只读 FD 不是持有者。** `lsof` 看到有进程打开着 `.git` 下的东西，要看 FD 模式：
写模式（`u`/`w`）才说明可能在写，只读（`r`）不算。本次现场持有只读 FD 的不是 git，
见下节。

## 4. 本次现场证据

- **锁文件**：0 字节，mtime 远超 10 分钟 → 判据 1、2 成立
- **git 进程**：`pgrep -x git` 无输出（exit 1） → 判据 3 的前半成立
- **`.git` 下的 FD**：唯一持有者是 **Cowork VM 本体**——
  `com.apple.Virtualization.VirtualMachine`（Apple Virtualization framework 的 XPC 服务），
  PID 52841，**只读 FD**，启动于 2026-08-26 13:45:42
- **该 VM 进程 `PPID = 1`** → 它的监管进程（启动它的那个 Cowork 会话）**已经死了**，
  进程被 launchd 收养，是个没人管的残留

三项判据全部成立 + VM 已失去监管 → Shao Peishen 拍板放宽并删锁。删后 git 立即恢复正常，
`git status` / `git log` 均正常，工作区 8 处改动完整无损。

## 5. ⚠️ 已知缺口：判据 3 对 VM 内部的 git 是盲的

**宿主机的 `ps` / `pgrep` 看不见 VM 里跑的进程。** Cowork 的 bash 在隔离 VM 内执行，
如果 VM 里有一个 git 正在提交、锁是它建的，那么在宿主机上：

- `pgrep -x git` → 空（VM 内进程不在宿主机进程表里）
- `lsof` → 只能看到 VM 本体这一个进程，看不到 VM 内是谁在用

**判据 3 此时会假成立**，三项凑齐，于是删掉一把真锁——正是规则原本要防的事故。

**补充判据（VM 场景专用）**：持锁方是 Cowork／虚拟机时，光看宿主机进程表不够，
必须额外确认**该 VM 进程本身已失去监管**：

```bash
ps -eo pid,ppid,lstart,comm | grep -i Virtualization
```

`PPID = 1` ＝ 启动它的会话已死、进程被 launchd 收养 ＝ VM 内不可能还有活着的 git 在提交。
`PPID ≠ 1`（挂在某个活着的 Cowork/Claude 进程下）＝ **VM 还活着，锁可能是真的，不许删。**

这条缺口目前**只有这一个补丁**，没有更强的手段——宿主机无法枚举 VM 内进程。
如果将来出现「VM 活着但 VM 内 git 已死」的孤儿锁，本判据给不出结论，只能进 VM 里查或问人。

## 6. 连带教训：并发协议第 4 条这类"绝对禁令"要带例外出口

第 4 条原文是纯禁令，没有任何例外分支。执行方越守规矩，卡得越死——
本次是「完全照做 → 整轮零产出」。**禁令是对的，缺的是"什么情况下不适用"那一半。**

同类规则写的时候顺手自问一句：**这条禁令防的那个前提，有没有可能不成立？**
不成立的时候按禁令做，会不会比违反它更糟？会，就必须把例外一起写进去。
