## 1. 日志落盘与轮转基座

- [x] 1.1 写测试（红灯基线）：在无控制台的执行路径下初始化日志系统后，指定目录里确实产生了非空日志文件，且应用 logger 与 uvicorn 三个 logger（`uvicorn` / `uvicorn.error` / `uvicorn.access`）的输出都落在其中（对应 spec「运行日志必须持久化且容量有界」的第一个场景）
- [x] 1.2 新增日志配置模块：一处 `dictConfig` 同时配置根 logger、应用 logger 与 uvicorn 三个 logger（design 决策 1），默认日志目录 `<AppDir>/logs/`、默认级别 INFO，零配置即可工作
- [x] 1.3 在 `app/config.py` 增加日志路径 / 级别 / 留存天数三个可选配置项，全部带默认值；`.env` 只做覆盖不做必填（design 决策 6），同步更新 `.env.example`
- [x] 1.4 接入按天轮转：`TimedRotatingFileHandler` + `backupCount = 留存天数`（默认 30）+ 单文件大小兜底上限（design 决策 2）
  - 实现偏离留痕：`backupCount` 实际取 **0**，留存改由 `purge_expired_logs()` 按 mtime 自行清理。原因是同日因大小上界二次轮转会产出 `app.log.<date>.N` 这类带序号单元，stdlib 的 `getFilesToDelete()` 用 `^\d{4}-\d{2}-\d{2}$` 匹配后缀、认不出它们，会把这些单元永久留下。本条要求的实质（留存期有上限且生效）不变。
- [x] 1.5 写轮转测试：构造跨轮转边界的写入，断言旧单元被保留为独立文件、新单元继续正常记录、无日志行丢失；断言保留份数不超过配置值
- [x] 1.6 在代码注释、`05-发布运行手册.md` 与部署文档三处写明单进程前提：**给 uvicorn 加 `--workers` 之前必须先更换轮转方案**（Windows 文件锁，design 决策 2 的代价）
- [x] 1.7 实现日志目录不可写时的降级：启动时探测可写性，不可写不崩溃、不阻断业务功能，并把"日志子系统降级"写进健康检查端点的返回内容（design 决策 5，对应 spec 第三个场景）。**幂等策略**：目录创建用"存在即跳过"语义，重复启动不报错、不覆盖已有日志文件
- [x] 1.8 写降级测试：日志目录不可写时，业务接口仍返回正常响应，且健康检查端点明确报告降级状态
- [x] 1.9 在 `app/main.py` 的导入期、早于 `create_app` 调用日志初始化；本地全量测试跑绿

- [x] 2.2 实现请求标识的生成与传播：ASGI 中间件在入口生成、写入 `contextvars`，`logging.Filter` 注入每条 record，格式串统一带上（design 决策 3）。业务代码的已有 `logger.*` 调用点一律不改
