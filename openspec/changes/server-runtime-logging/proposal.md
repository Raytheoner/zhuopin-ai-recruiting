## Why

`.51` 现网**不存在任何日志文件**。计划任务以 SYSTEM 账户直接执行 `uvicorn.exe`，stdout/stderr 没有重定向、也没有控制台可以承接，因此进程写出的每一行日志都直接进了虚空。后果是双重的：

**一、已经付出过代价。** 2026-08-18 的现网取证（`docs/findings/2026-08-13-sqlite-事务归属冲突.md` 第 8 节）确认，SQLite 事务归属冲突在修复前的现网实际触发过两次（`1cabfb91` 的 2026-08-12 09:49:09、`41909b40` 的 2026-08-10 07:16:00），表现为幂等记录已提交而 `outbox` 缺行——那两轮的回复永久丢失，用户侧只看到「问了一句没回应」，会当成网络问题重试，不会报障。这两次是**靠数据库不变式反推**出来的，不是靠日志查出来的。同一份修复给 `app/storage/idempotency.py` 加的 `logger.error("rollback failed …")` 兜底告警，在现网同样什么都不会留下。换句话说：现在再发生一次同类事故，我们仍然只能事后靠 SQL 考古，而且只有在有人想到去查的时候才会发现。

**二、M2 的前置。** 部署约束第 5 条要求 M2 起处理真实简历前具备可识别到人的登录与访问留痕。业务侧的审计事件由 `ai-audit-trail-and-outbound-gate` 承载，但那套留痕本身也要写到某个地方、也要保证不把候选人个人信息以明文散落到运行日志里。运行时日志通道是它的地基，地基现在是空的。

现在做，是因为 M1 试运行已经跑过 3 位业务经理、现网有真实使用数据，而下一次偶发 500 仍然无法追溯；等到 M2 接真实简历再补，等于在有个人信息的前提下调试日志脱敏规则。

## What Changes

- 新增应用层日志配置模块：进程启动时统一初始化 Python `logging` 与 uvicorn 的 logger，日志同时写到文件与 stdout，文件路径可配置
- 日志文件按大小或日期轮转，保留份数可配置，磁盘占用有上界（现网是生产服务器，不能让日志无限增长把磁盘写满）
- 新增 `request_id`：每个 HTTP 请求生成一个标识，贯穿该请求处理期间产生的所有日志行，并回写到响应头，便于把用户报告的一次异常对应到日志段落
- 未捕获异常统一记录：500 响应必须留下一条含 `request_id`、异常类型、完整堆栈的错误日志；已知的业务上下文（`job_id` / `thread_id`）在可得时一并记录
- 新增日志脱敏规则：候选人与岗位画像的内容字段不得以明文进入日志；受控字段只记录标识与长度/哈希一类的非还原性摘要
- 新增日志留存期上限，超期日志自动清理，留存期可配置
- 修改 `deploy-server.ps1` 的计划任务定义，把日志目录、日志级别、留存配置接进部署流程；日志目录不进代码同步白名单（属运行时数据，与 `data/` 同等对待）
- 新增测试：验证日志确实落到文件、验证轮转触发、验证 `request_id` 贯穿、验证 500 留下堆栈、验证受控字段在日志中不出现明文

## Capabilities

### New Capabilities

- `runtime-observability`：服务进程的运行时可观测性契约——日志必须持久化到可查询的位置且容量有界、一次请求的所有日志可通过单一标识串联、服务端错误必须留下可定位到具体会话的证据、日志内容受个人信息脱敏与留存期约束

### Modified Capabilities

（无。`openspec/specs/` 目前只有 `effect-transaction-integrity` 一条，本变更不改变它的任何需求。本变更新增的是横切的运行时行为，不改动 M1 已有的对外接口语义与业务流程。）

## Non-goals（不做什么）

- **不做简历访问留痕与业务审计事件**——「谁在什么时候看了谁的简历」、`analysis_run` / `criterion_score` / hash-chain 防篡改，全部由 `ai-audit-trail-and-outbound-gate` 承载。本变更只提供运行时日志通道，两者边界是：**业务审计是结构化的、需要举证的、不可删的；运行时日志是排障用的、会轮转过期的**。不要把审计事件写进会被轮转清掉的运行日志。
- **不做登录与鉴权**——`app/middleware/auth.py` 的空壳不动，企微 OAuth SSO 待两侧共同决定。`request_id` 不是身份，能串联请求但不能回答「是谁」，M2 前的登录仍是独立阻塞项。
- **不做主动告警**——关键错误发企微、定期跑不变式自检（`effect_log` ↔ `outbox` 校对），本次不做。理由：企微通道尚未接入，且没有日志先落盘，告警也没有可引用的证据。留作后续变更，本次的日志格式要为它留出可被程序解析的形态。
- **不引入日志聚合基础设施**——不上 ELK / Loki / Sentry，不引入需要额外常驻进程的组件。目标服务器是没有 Docker 的 Windows，部署形态是 venv + 计划任务（部署约束 4），本变更维持这个形态。
- **不改变部署形态本身**——仍然是 venv + Windows 计划任务 + scp 推送，只修改计划任务的定义（加日志相关参数），不换运行方式、不加服务包装器。
- **不做日志查询界面**——现阶段查日志靠 RDP 或 ssh 看文件，不做 Web 端日志浏览。
- **不追溯修补已发生的两次丢行**——那两轮属于修复前的演示会话，补写会破坏幂等语义，已在 findings 第 8.2 节记录并结案。

## 合规影响说明

本变更**不新增个人信息的处理场景**，但它决定个人信息**是否会被写进第二个地方**，因此必须按处理个人信息的标准来设计：

- M1 阶段的岗位画像已含业务经理输入的自由文本，M2 起会含候选人简历内容。运行日志若原样打印请求体或状态对象，等于在数据库之外再制造一份**未受控、会被 scp 与备份顺带复制**的个人信息副本。因此脱敏不是可选项，是本变更的核心需求之一。
- 日志留存期上限对应 PIPL 的最小必要与存储限期原则：排障需要的时间窗远短于业务数据的保存期，两者不应共用同一套留存策略。
- 日志文件与 `data/` 同属运行时数据，不进代码同步白名单，避免生产日志被反向同步到开发机——那会构成一次未经授权的个人信息转移。
- 本变更不涉及数据出境（日志只落在 `.51` 本地文件系统），不涉及人脸/表情数据，不涉及自动化决策。

## Impact

**受影响代码**
- `app/main.py`——进程启动时的日志初始化入口
- `app/web/server.py`——`request_id` 中间件与未捕获异常处理器的挂载点
- `app/config.py`——新增日志路径、级别、轮转与留存期配置项
