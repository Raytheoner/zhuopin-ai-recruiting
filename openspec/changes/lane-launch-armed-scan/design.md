## Context

发车链路的现状与五次实证见 `proposal.md` — Why。这里只补三条约束设计的事实：

1. **编排文件的待跑标注是 `> 泳道：<泳道名>`**，紧贴 opener 代码块前一行；执行器跑完由 `mark_done` 就地改写成 `> ✅ 已完成 …（脚本自动摘，不再进 run-lanes）`。`run-lanes.sh` 用 `grep -c '^>[[:space:]]*泳道：'` 数待跑数（`PLAN_LANE_M`），并有 Σ=N=M 的条目总数自检。
2. **`lane-launcher.sh` 已经把「参数白名单 + 原子认领 + 并发推迟」这三样做对了**，且每一处都带着踩坑注释（`IFS` 永久污染、WatchPaths 自触发导致双实例、`.deferred` 不自动重试）。本设计复用这套语义，⛔ 不重新发明。
3. **`run-lanes.sh` 有自拷贝执行**（第十二批实证：bash 按字节偏移边跑边读，运行期改脚本会自我损坏）。扫描器同样以 `exec` 前自拷贝或只读方式调用它，⛔ 不在运行期改动它。

关键的环境事实：**Claude 与 Shao Peishen 以同一个 macOS 用户身份运行**。扫描器能读到的任何密钥，Claude 也能读到。这一条决定了令牌的性质。

## Goals / Non-Goals

**Goals:**

- 把授权动作与发车时刻解耦：可提前武装、可批量武装、可从任意能 push 的地方武装
- 授权与被执行内容强绑定：授权对象改了，授权就失效
- 每一次发车可事后归因到一次具体的授权动作
- 与既有请求文件路并存，两条路互不依赖

**Non-Goals（设计层面，`proposal.md` 的范围之外再加）：**

- ⛔ 不追求密码学意义上的不可伪造。理由见下方 Decision 1，这是被环境否决的，不是被省略的
- ⛔ 不引入常驻进程、端口、数据库。扫描器是"唤醒→判定→要么发车要么退出"的短命进程
- ⛔ 不做令牌的图形界面或交互式签发向导

## Decisions

### Decision 1：令牌的性质是「可归属 + 防篡改」，不是「不可伪造」

**选择**：令牌是一份提交进 git 的明文文件，记录签发者、签发时间、有效期、覆盖编号、每条 opener 正文的内容摘要、以及受白名单约束的执行参数。校验只用摘要比对与时间窗，**不引入密钥**。

**为什么不用 HMAC / 签名密钥**：任何被扫描器读取的密钥都存在于本机文件系统，而 Claude 以同一用户身份运行、具备完整文件读取能力。加一层 HMAC 只会制造"这是硬边界"的错觉，实际强度不变——**伪装成安全机制的安全机制比没有更危险**，因为它会让下游按错误的强度去依赖。

**为什么不用 GPG 签名**：同理。除非私钥带 passphrase 且每次签发要人当场输入，那就退化成 Decision 备选 C（硬闸门），已被 Shao Peishen 排除（2026-09-09 裁决：取武装令牌）。

**真正的安全边界在别处**，本设计承认并依赖它：Auto Mode 分类器仍然拦着看护者直接发车的所有路径。令牌解决的是"人必须在场"这个**可用性**问题，不是"AI 会不会越权"这个**安全**问题。spec 里为此专门立了一条要求，强制这个边界被显式写出来。

**代价**：一个被入侵或被 prompt 注入的 session 理论上能自签令牌发车。缓解见 Risks。

### Decision 2：只读 git 已提交版本，不读工作区

**选择**：扫描器用 `git show <ref>:<path>` 取编排文件与令牌，不读工作区文件。

**为什么**：授权链必须锚在可追溯对象上。工作区文件可被任何进程静默改写且不留痕；已提交对象有 hash、有作者、有时间。这也顺带解决了"编辑到一半被扫到"的竞态——半截编排永远不会被发车。

**备选（否决）**：读工作区 + 要求 clean tree。否决理由：并发泳道跑起来后工作区几乎永远不 clean（第十五批实测跑完仍有一个未提交文件），这条判据会让扫描器长期瘫痪。

### Decision 3：定时唤醒（`StartInterval`），不用 `WatchPaths`

**选择**：新增一个独立的 LaunchAgent，用 `StartInterval` 定时唤醒扫描器。

**为什么不复用现有的 `WatchPaths`**：`WatchPaths` 盯的是 `.claude/handoff/launch/` 目录变化，而新机制的触发源是 git 提交——提交发生在仓库任意位置，没有一个稳定的目录可盯。且 `WatchPaths` 的自触发问题（脚本自己写文件再次触发自己）已经在 `lane-launcher.sh` 里付出过代价，定时唤醒天然没有这个问题。

**为什么是独立的 LaunchAgent 而不是给现有 plist 加时间触发**：现有 plist 刚在 `496f55e` 修好 `AbandonProcessGroup` 与绝对 `PATH` 并经 17 条测试锁住触发契约（含 `test_build_plist_keeps_trigger_contract`）。往里塞第二种触发方式会同时改动那条刚验证过的路径。两个 Label 各管一件事，故障域也分得开。

**间隔取值**：留给实现期定，量级在分钟。⛔ 不做成秒级——扫描器每次唤醒都要跑 git 与 pgrep，秒级轮询在无事可做时是纯浪费。

### Decision 4：摘要不匹配整批拒绝，不做部分执行

**选择**：令牌覆盖的任一条 opener 正文摘要对不上，整批拒绝。

**为什么不"只跑对得上的"**：那等于让一次授权在其覆盖范围被部分篡改后仍然生效，授权对象与执行对象脱钩。且部分执行会让泳道集合与编排时的触碰区分析不再成立——触碰区是按整批算的，少跑一条可能让另一条的"零重叠"前提失效。这与 `lane-launcher.sh` 白名单"⛔ 不做跳过这个参数继续，半截参数比不跑更危险"是同一条原则。

### Decision 5：一次一销用原子重命名，与既有认领协议同构

**选择**：消费令牌 = `mv` 成另一个后缀，失败即视为被别的实例抢走，直接退出。

**为什么**：`lane-launcher.sh` 已经用这套解决过"两个实例看到同一请求"，注释里写明了 `mv` 在源文件已被搬走时返回非 0 就是那个原子判据。同构能让两条路的失败模式一致，读代码的人不用记两套。

### Decision 6：扫描器只读 git，一次写操作都不做

**选择**：扫描器不 `pull` / `commit` / `push` / `checkout`。令牌消费用文件重命名（工作区动作），不产生提交。

**为什么**：无人值守进程一旦能写 git，就能在无人看管时把仓库带到意外状态；而并发泳道正在同时读写同一个仓库。`--autostash` 之类的自愈手段在并发下有已知的破坏性（CLAUDE.md 并行铁律 3 与 `git stash` 禁令）。扫描器的职责边界就到"决定要不要发车"为止。

**副作用**：令牌被消费的事实不进 git 历史。用日志留痕代替，spec 的可归属性要求由"日志 + 已消费令牌文件"共同满足。

## Risks / Trade-offs

- **被注入或失控的 session 自签令牌发车** → 分类器仍拦着直接发车路径，是独立的第二层；令牌与日志留下完整归因链，事后可查；令牌绑定内容摘要，无法用一枚旧令牌授权新内容。⛔ 但必须承认这不是硬防护，spec 已强制把这条边界写进文档。
- **定时扫描让"提交"这个动作有了副作用** → 只有同时存在有效令牌才发车，而令牌是显式的、一次性的、带有效期的。单纯提交编排不发车（spec 首条要求）。
- **令牌过期导致该跑的批次静默没跑** → 每次拒绝必须留痕（spec 有专条），且"扫过且无事可做"与"没被唤醒"在日志里可区分。⛔ 不做自动续期——自动续期会让有效期形同虚设。
- **两个 LaunchAgent 各自可能发车，撞成两个执行器** → 两条路都在发车前跑同一条并发判定（pgrep 执行器进程），且都在 `.git/index.lock` 存在时推迟。这条判据对 VM 里的 git 是盲的（`docs/findings/2026-08-26-index-lock-孤儿锁判据.md`），但本机制只在本机 launchd 下运行，不涉及 VM。
- **扫描器本身出错导致整条发车链静默失效** → 装机验收要求端到端实跑一次（见 Migration Plan），且日志可区分"没被唤醒"。
- **间隔太长导致武装后迟迟不发车** → 有效期与间隔的关系在实现期一并定，验收用例覆盖"武装后在一个间隔内发车"。

1. 实现扫描器与令牌工具，单测覆盖 spec 的每条场景（TDD，红在前）
2. 扩展 `scripts/install_lane_launcher.py`：⛔ 不动现有 `WatchPaths` 分支与 `496f55e` 修好的两处，只新增一个 Label 的安装/卸载
3. **Shao Peishen 在 Terminal 手工跑一次安装**（起/换 LaunchAgent 属安全配置，Claude 不代做）
4. 端到端验收：签发一枚覆盖某条真实待跑泳道的令牌 → 在一个扫描间隔内确认执行器起来、日志目录建出、令牌被标记消费
5. 落档：`.claude/skills/lane-dispatch/SKILL.md` 发车段落追加第四条实证（三条历史结论全部保留），`CLAUDE.md` 若受影响当次改

**回滚**：卸载新增的那个 LaunchAgent 即可，请求文件路与 Run 按钮路原样可用。本变更不改 `run-lanes.sh` / `lane-launcher.sh`，回滚不涉及代码回退。

## Open Questions

- **扫描间隔与令牌默认有效期的具体取值**。可安全推迟：不改变任何 spec 要求、不改变架构、不改变任务拆分，只是两个常量，实现期结合实际批次节奏定，验收用例只要求"武装后在一个间隔内发车"。
- **令牌文件放在仓库内还是仓库外**。倾向仓库内（可归属性依赖 git 历史），但若放仓库内会让令牌进入并发泳道的触碰区，需在实现期核一次是否会与泳道提交撞车。两种放法都不改变 spec 的任何一条要求。
