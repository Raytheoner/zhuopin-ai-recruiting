## Context

动机与范围见 `proposal.md`。这里只列塑造技术方案的现状与约束：

- **参考对象是只读的、且不在本机**。`wecom-aibot-service` 已随「企业AI转型」仓库迁到 GitHub（`https://github.com/Raytheoner/zhuopin-ai-transformation`，分支 `master`，路径 `5-平台底座/wecom-aibot-service/`，中文路径需 percent-encode），只能 `WebFetch` 按文件级路径读，**没有本地副本，不能 grep 模糊搜索**。本设计引用它的事实全部来自该服务的 `CLAUDE.md` 与本仓库 `06-企业AI转型资产借鉴清单.md` §三。
- **协议形态与本项目铁律 6 的默认假设不同**。企微"智能机器人"走 WebSocket 长连接（纯出站、无入站端口、鉴权靠 SDK 内置 BotID/Secret），协议路径上**不存在**"签名校验 + 落库 + 返回 200"这一步。铁律 6 的意图（外部消息先落库再处理，不在回调线程里做业务）仍然成立，落地方式必须按 WS 特性重写，不能照抄字面。
- **协议不提供离线补推**。参考服务的 `gap_alert.py` 明确写死"断线期间的消息永久丢失"。这是协议保证的上限，不是对方实现不够好。
- **本仓库已有幂等机制**：`app/storage/idempotency.py` 的 `idempotent_effect(node_name)` 装饰器 + `effect_log(effect_key PRIMARY KEY, thread_id, node_name, business_key, applied_at)` 表与唯一索引（`app/storage/db.py:59-67`），幂等键形态 `{thread_id}:{node_name}:{business_key}`。
- **部署脚本按白名单同步**：`sync-to-server.sh:42-50` 的 `SYNC_PATHS` = `app` / `scripts` / `requirements.txt` / `pyproject.toml` / `.env.example` / `deploy-server.ps1` / `sync-to-server.sh`；`EXCLUDE_NAMES`（`:58`）排除 `data` / `logs` / `venv` / 缓存。`deploy-server.ps1` 在 `.51` 上按根 `requirements.txt` 装依赖。
- **Python 版本被钉死**：`pyproject.toml` 的 `requires-python = ">=3.14,<3.15"`，理由是"测试环境 = 运行环境"。而 aibot SDK 的 Python 支持范围未知。
- **本机是 macOS**，进程守护用 launchd（不是 Windows 计划任务）。

## Goals / Non-Goals

**Goals：**

- 让汤丽萍在原有企微群/私聊里发消息发文件，**行为完全不变**，材料自动归档并生成可追踪的值守任务行。
- 重复投递不产生重复副作用；协议层丢失被**显式暴露**而不是被幂等机制掩盖成"看起来没事"。
- 参考服务的六个真实生产 bug 里，能靠**结构选择**消灭的一律靠结构消灭，不靠"实现时留意"。
- 结构上不可能被误部署到 `.51`、不可能被误当成产品功能。

**Non-Goals（设计层面的额外边界，范围类边界见 proposal「Non-goals」）：**

- 不追求"零消息丢失"。协议做不到，设计目标是**丢失可被发现**。
- 不追求与 Windows 侧的实现同构。同构会制造"两边必须一起改"的隐性耦合，共享的是做法不是代码。
- 不做可插拔的通道抽象层（只有企微一个通道，抽象层是空成本）。

## Decisions

### D1 · BotID 是否与 Windows 共用 → **结论：不共用。Mac 侧独立注册一个新的 aibot 应用。**

`HR_LIAISON_BOT_ID` / `HR_LIAISON_BOT_SECRET` 是一对全新凭据，与 Windows 侧那套**没有任何共享**，由 Shao Peishen 在企业微信管理后台注册后自行填入本机 `.env`。

**为什么不共用**：企微智能机器人是 WS 长连接协议，同一 BotID/Secret 是否允许两台机器同时建长连接**没有官方文档确认**，也没有把握用测试验证清楚——可能的失败模式包括消息重复投递、后连的顶掉先连的、或直接被拒。过渡期 Windows 那套还在服务现役的质量/采购/财务三个部门，**不值得为了省一次注册去冒这个不确定的风险**。

**考虑过的替代方案**：
- *共用凭据 + 按发送人分流*（Mac 只处理 HR 的人，Windows 只处理它那三个域）：把不确定的协议行为放在两套系统的正确性前提里，且"顶掉先连的"这种失败模式对现役部门是静默的服务中断。否决。
- *先做兼容性实验再决定*：实验要在生产 BotID 上做，实验本身就是风险；且负面结果需要长时间观察才能确认（例如"偶发重复投递"）。否决。

⛔ 本条是结论，不是待选项。design 复审时不再重开。

### D2 · HR 白名单范围 → **结论：白名单 = {汤丽萍, 邵培申}，两人。聂鑫／王寒月／陈承不入。**

| 人 | 是否入白名单 | 理由 |
|---|---|---|
| **汤丽萍** | ✅ 入 | HR 侧唯一已确认的 AI 专员，是材料交换的对手方。她是本服务存在的理由。 |
| **邵培申**（Shao Peishen） | ✅ 入 | 工具主人。自测、发指令、验证链路都需要自己这条通道；不入白名单会导致"要测试只能麻烦专员配合"。 |
| **陈承** | ❌ 不入 | 他已在 Windows 侧白名单里（IT 域）。同一个人进两套白名单，他一条消息会在两套系统里各生成一条互不知情的任务行——重复劳动且状态永久不同步。他若有 HR 事务，走 Windows 那套既有通道。 |
| **聂鑫** | ❌ 不入 | 群成员身份 ≠ 材料提交责任人。当前没有任何已确认的 HR 材料提交职责落在他身上。 |
| **王寒月** | ❌ 不入 | 同上。 |

**判据（为什么默认从紧）**：白名单是 fail-closed 准入闸，两个方向的代价**不对称**——
- 少放一个人：他发的消息仍然**被归档**，并收到礼貌回复，只是不生成任务队列行。补救成本 = 配置文件加一行 + 重启，当天可解决，且缺口是**可见的**（他会收到礼貌回复，会来问）。
- 多放一个人：未经确认的人可以往值守任务队列里写行，污染队列且**不易被发现**（队列多出来的行看起来和正常行一样）。

不对称就按可逆的那一侧默认。

⛔ 本条是结论，不是待选项。追加成员的正确路径是"确有提交职责时按名录单条追加并留痕"，不是把群成员整批放进去。

### D3 · 可靠性模型 → at-least-once + 幂等 effect，**且协议层丢失单独暴露**

沿用本仓库铁律 1 的机制，**不照抄参考服务的 at-most-once 模型**：

- `thread_id` = 消息来源会话标识（私聊取 `userid`，群聊取 `chatid`）。
- `business_key` = 企微 `msgid`（协议内单条消息的唯一标识）。参考服务只把它当归档文件名后缀，本实现把它当**真正的幂等键组成部分**。
- 幂等键 = `{thread_id}:{node_name}:{business_key}`，形态与 `app/storage/idempotency.py` 逐字一致。
- 每个有副作用的动作独占一个 `effect_*` 函数：`effect_archive_message` / `effect_enqueue_task` / `effect_send_group_notify`。计算类（白名单判定、内容归一化、长度守卫判定）一律 `compute_*` 纯函数，无副作用。
- **幂等记录与业务写同一连接、同一 `BEGIN` 提交**。本服务不引入 checkpointer（见 D6），因此该连接上**不存在第二个事务管理者**——`docs/findings/2026-08-13-sqlite-事务归属冲突.md` 那类冲突在这里结构上不会发生。
- **reviewer 判据**：每个 `effect_*` 的 `effect_log` 条数与其业务表行数按 `thread_id` 恒等，且该不变式有测试覆盖。

**文件写与 SQL 写不可能同事务**（文件系统不参与 SQL 事务），顺序因此被钉死：

1. 附件写临时文件 → `fsync` → **原子 `rename`** 到最终路径（路径含 `msgid`，天然幂等：目标已存在即视为已完成）；
2. 然后在**一个事务**里写消息行 + `effect_log` 行并提交。

⛔ 顺序不许反。"文件已落、DB 行未写"是可收敛的中间态（重跑时 rename 幂等、DB 行补上）；"DB 行已写、文件缺失"是不可恢复的谎——台账说材料收到了，材料却不在。

**协议层丢失单独处理，不进幂等的账**：服务维护存活戳并**区分"真断线"与"空闲"**（参考服务曾混淆此二者、后修正）。检测到连接中断窗口时，MUST 记录该窗口的起止时间并显式告警"这段时间可能漏消息，请重发"。⛔ MUST NOT 因为"我们有幂等了"就把这个缺口当成已覆盖——幂等防的是重复，不是丢失。

### D4 · 归档形态 → 细粒度键 + 字节流，**结构性避开两个生产 bug**

- **归档路径**：`data/liaison/archive/<thread_id>/<yyyymmdd>/<msgid>__<原文件名>`。键的最细一级是 `msgid`。⛔ 禁止任何"按天一个文件"或"按人一个文件"的粗粒度落点——参考服务的生产 bug「归档覆盖」（同人同天多条消息互相覆盖）就是这么来的，日期在本路径里只是**分目录**，不是键。
- **附件一律按字节流读写**（`rb`/`wb`）。完整性校验只用**字节长度 + SHA-256**，⛔ **禁止任何 UTF-8 解码校验**——参考服务的生产 bug「二进制判误」正是把合法的 `xlsx`/`pdf` 拿去做文本解码后误判为损坏。原始后缀原样保留，不按内容猜类型。
- **文件名归一化只处理路径安全**（去掉路径分隔符、控制字符、前后空白，长度截断保留后缀），⛔ 不因为"看起来像乱码"就改写或拒收。

### D5 · 存储落点 → 独立 `data/liaison.db`，**不与 `data/demo.db` 混库**

- 本服务是常驻独立进程；`demo.db` 由 FastAPI 应用持有。两个进程并发写同一个 SQLite 文件 = 写锁竞争 + `database is locked`，而且是间歇性的、难复现的那种。
- 产品库里出现开发期工具的表，会让"这张表要不要跟着产品上线"变成一个每次都要重新回答的问题。库边界替它一次性回答掉。
- `liaison.db` 里自建一张与 `app/storage/db.py:59-67` **同构**的 `effect_log`（同列、同主键、同唯一索引），并直接复用 `idempotent_effect` 装饰器——复用的是机制与代码，不是同一个文件。
- 复用方向**单向**：`tools/liaison` 可以 `import app.storage.idempotency`，⛔ `app/` 下任何模块不得 import `tools/`。

### D6 · 不引入 LangGraph

本服务是"一条消息进来 → 归档 → 入队 → 可能通报"的线性处理，没有多分支编排、没有需要恢复的长流程。铁律 1 的动机（恢复时整节点重跑导致副作用重复）在这里由另一个成因承担——**重连后 SDK 可能重投同一 `msgid`**——而应对手段是同一个：`idempotent_effect`。引入 checkpointer 只会带来 D3 里刚刚被结构消除掉的事务归属冲突。

**考虑过**：用 LangGraph 以"与产品代码同构"为收益。否决——同构本身不是收益，代价是把一个已知的事故成因请回来。

### D7 · 与四个活文档能力的边界（逐条给结论，不留隐藏假设）

| 活文档能力 | 关系 | 结论 |
|---|---|---|
| `effect-transaction-integrity` | **沿用，不修改** | 其"单一事务边界所有权""幂等键与业务写原子提交"两条要求在本服务里天然满足（无第二个事务管理者）。本服务的 `effect_*` 测试须覆盖同样的不变式。 |
| `outbound-approval-gate` | **不落在门禁内** | 依该 spec「门禁覆盖范围」要求原文：门禁只覆盖候选人拒信与面试邀约，"面向内部员工的通知不在门禁范围内"。本服务全部外发对象是内部同事。⛔ 但这**不是**"无约束"：`liaison-group-notify` 自带限流与长度守卫，且本服务 MUST NOT 用于向候选人发送任何内容。 |
| `ai-decision-audit` | **不适用** | 本服务不做任何 AI 评分、不调用 LLM，不产生 `analysis_run` / `criterion_score`。 |
| `runtime-observability` | **借用做法，不受其要求约束** | 它的要求文本针对产品服务的 HTTP 请求链路（request id 串联等）。本服务是常驻长连接进程，没有请求边界。借用的做法是：日志落到有界的轮转文件、个人信息脱敏、留存期有上限。 |

### D8 · SDK 选型 → `wecom-aibot-python-sdk`，但**先验兼容性再写业务代码**

选它的理由与参考服务一致：SDK 内置 WS 连接管理、心跳（30s 间隔、2 次无响判死）与指数退避重连（封顶 30s），这些是协议细节而非业务逻辑，自己实现只会重复踩官方已处理的边界。Windows 侧在用 **v1.0.2** 并已通过满周灰度。

⚠️ **真实风险**：SDK 文档未明确 Python 支持范围（按依赖链推断 3.8+），而本项目钉死 `>=3.14,<3.15`。

**因此 tasks 第 1 章的第一件事就是兼容性实测**（装得上、能建连、能收发），在此之前不写任何业务代码。**退路已定**（不留成 Open Question）：SDK 在 3.14 上不可用时，按企微官方 WS 协议自建最小客户端（连接 + 心跳 + 退避重连 + 消息解析），范围只覆盖本服务用到的消息类型，**不做通用 SDK**。退路的代价（自己维护心跳与重连）已被接受，理由是版本钉死这条约束的来源（"测试环境 = 运行环境"）比"少写一个客户端"更重要。

⛔ 不许为了装上 SDK 去放宽 `requires-python`——那会把整个产品的版本对齐前提改掉，代价与本工具的收益完全不成比例。SDK 只装进 `tools/liaison/` 自己的环境。

### D9 · 群通知 → 限流 + 长度守卫，**两处参考实现的空白一并补上**

- **限流**：企微群机器人官方限流 **20 条/分钟**（超限返回 `errcode 45009`）。本实现用令牌桶（容量 20、按 20/60s 补充）主动节流；真的收到 `45009` 时按指数退避重试（1s→2s→4s→8s，最多 4 次）；4 次仍失败即写入待重发记录并告警，⛔ 不静默丢弃。
- **长度守卫按字节计，且两条通道各自独立配置**：aibot 通道服务端限额 **20480 字节**（Windows 侧 2026-08-28 实测）；群机器人 webhook 的 markdown 上限约 **4096 字符**（企微官方限制）。⛔ 不共用一个常量——两个数字来源不同、单位不同（字节 vs 字符），共用等于给其中一条通道埋一个静默截断。
- **超限降级**：超限时降级为"提要 + 附件"；提要本身仍超限、或没有附件通道可用时**整条拒发并告警**，⛔ 不静默截断丢内容。
- **凭据分离**：群 webhook 真实 URL 只落 `.env`；版本管理里的配置只写**环境变量名**（照搬参考服务 `department_group_mapping.yaml` 的秘密隔离做法）。

### D10 · 落点与依赖隔离 → 让目录和依赖清单充当结构性门禁

- 代码落 **`tools/liaison/`**。⛔ 不落 `app/`（产品交付物），⛔ 也不落 `scripts/`——`scripts` 与 `app` **都在** `sync-to-server.sh` 的 `SYNC_PATHS` 白名单里，放进去就会被推到 `.51`，而本服务明确永不部署 `.51`。`tools/` 不在该白名单里，因此**结构上不可能被同步**。
- 依赖落 **`tools/liaison/requirements.txt`**，⛔ 不进根 `requirements.txt`——根清单会被同步且被 `deploy-server.ps1` 在 `.51` 上 `pip install`。这条与参考服务的结构性门禁 D8（`pyproject.toml` 刻意不含连接器 extra）同一手法：**让清单本身承担约束，不靠人记得别装**。
- ⛔ 不改 `sync-to-server.sh` / `deploy-server.ps1` 去"排除 tools"——不在白名单里已经足够，改部署脚本反而制造一个必须维护的黑名单。

### D11 · 队列真身 = SQLite 表，Markdown 只作只读导出视图

参考服务的三个生产 bug——「队列越界写入」（消息含竖线破坏表格结构）、「队列追加并发覆盖」、以及需要靠"竖线归一化 + 9 条边界列数自检"才能挡住的结构损坏——**全部源于同一个根因：拿 Markdown 表格当数据库**。本实现不复现这个根因：

- 队列真身是 `liaison.db` 的 `liaison_task` 表，入队走 `effect_enqueue_task`（幂等 + 事务）。任意消息内容（含竖线、换行、控制字符）都只是列里的一个字符串值，**不可能破坏结构**——竖线归一化在这个形态下根本不需要。
- Markdown 只是**导出物**，一个只读渲染命令。渲染时对内容做转义。
- **单向**：人在导出的 Markdown 里改了什么，⛔ 不回写数据库。避免"两份真身"。
- 状态语义**照搬**参考服务已验证的三态（`🆕 待发` / `⏸ 暂缓` / `✅ 已推送`）——这一条是它验证过的资产，值得沿用；⛔ 但存的是枚举值，emoji 只出现在渲染层。

### D12 · 进程守护 → launchd `KeepAlive`，不自实现退避脚本

内层重连交给 SDK 默认机制（D8）。进程级守护用 launchd（`KeepAlive` + `ThrottleInterval`）。⛔ 不移植参考服务的三级退避重启脚本（1min/5min/15min）——那是因为 Windows 计划任务没有 KeepAlive 语义才自己写的，launchd 原生就有；移植等于把别人平台的缺口一起搬过来。

### D13 · 数据留存 → 归档与消息 180 天，可配置，退役即清理

`HR_LIAISON_RETENTION_DAYS` 默认 **180**。选 180 天而不是与日志的 30 天对齐：日志是运行证据，归档是**工作材料**，一个开发阶段的材料回溯窗口按季度量级算才够用。**非终态**队列行（🆕 待发 / ⏸ 暂缓）不参与自动清理（是活的工作台账、量小、状态有意义）；**终态（✅ 已推送）且超期**的队列行连同其归档一起清（2026-09-09 Shao Peishen 裁决一，见 `docs/findings/2026-09-09-Shao-Peishen-裁决-留存冲突B与TD20改法.md`：原口径「队列行不参与自动清理」会让名单内发送人的归档因外键永远清不掉，与本条的 180 天相悖）。本工具随系统上线退役，退役时归档与库一并清理（proposal「合规影响说明」）。

## Risks / Trade-offs

- **[SDK 在 Python 3.14 上装不上或建不了连]** → tasks 第 1 章先做兼容性实测再写业务代码；退路（自建最小 WS 客户端）已在 D8 定完，不阻塞后续任务拆分。⛔ 不放宽 `requires-python`。
- **[断线期间的消息永久丢失（协议保证的上限）]** → 无法消除，只能暴露：中断窗口记录 + 显式"可能漏消息"告警 + 主动请对方重发。⛔ 不允许在文档或代码注释里把它描述成"已被幂等覆盖"。
- **[白名单从紧，可能挡掉真的该收的人]** → 这是 D2 刻意选的方向，且缺口可见（对方收到礼貌回复）、可当天修复（配置加一行）。反向错误不可见，代价更高。
- **[两套系统各管各的，同一材料可能被两边都收到一次]** → 接受。两套的域不重叠（Windows 管质量/采购/财务，Mac 只管 HR），跨域材料本来就该由发送人选通道；做两端对账的成本远高于偶发重复的代价（proposal 已把"两端对账"列入 Non-goals）。
- **[`tools/` 不在同步白名单 ⇒ 将来若真需要部署本服务，会"忘了它不在白名单里"]** → 这是刻意的：本服务永不部署 `.51`（Shao Peishen 2026-08-13 口径）。若口径将来真的变了，那是一次需要本人拍板的决策，而"必须先改白名单"正好构成一道显式的闸。
- **[群通知的令牌桶是进程内状态，进程重启即清零，重启瞬间可能突发超限]** → 收到 `45009` 的退避重试兜住（D9）。⛔ 不为此引入持久化限流状态——复杂度与收益不成比例，而退避已经覆盖了这个窗口。
- **[归档目录随时间增长占满磁盘]** → D13 的留存期清理；清理任务失败时告警，⛔ 不静默跳过。

## Migration Plan

**这不是迁移一个运行中的系统，是在 Mac 上新建一套并让 Windows 那套继续跑。两边不存在切换时刻，也不需要数据迁移。**

1. **前置（只有 Shao Peishen 能做）**：在企业微信管理后台注册**新的** aibot 应用，取得 BotID/Secret；确认"人力AI保障组"的 chatid 与群机器人 webhook URL。填入本机 `.env`。
2. **兼容性实测**（tasks 第 1 章）：SDK 在 Python 3.14 上装得上、能建连、能收发。不过 → 走 D8 退路。
3. **单机灰度**：白名单先只放邵培申自己，自测归档/入队/通报三条链路，确认幂等不变式（`effect_log` 条数与业务行数恒等）。
4. **加入汤丽萍**：配置加一行，重启。告知她"照原样在群里发就行，不用改任何习惯"。
5. **观察窗口**：一周。观察项 = 漏消息告警是否误报、限流是否被触发、归档是否有重名冲突。

**回滚**：停掉 launchd job 即回到今天的状态（人工在群里交换材料）。归档与 `liaison.db` 留在本机不删——回滚是"停止值守"，不是"销毁台账"。⛔ 回滚不需要动 Windows 那套的任何东西（两边零共享，这正是 D1 的收益）。
