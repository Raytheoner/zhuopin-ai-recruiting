## Context

现状见 `proposal.md` — Why。技术上需要顾及的约束有四条，它们共同排除了大部分"常规做法"：

1. **运行形态是 Windows 计划任务 + venv，没有 Docker、没有常驻日志代理**（部署约束 4）。`Register-ScheduledTaskAction` 的 `-Execute` 直接拉起 `uvicorn.exe`，中间没有 shell，因此 `> app.log 2>&1` 这类重定向在计划任务定义里**根本没有地方写**。
2. **单进程**。计划任务里 uvicorn 没有 `--workers`，全程一个进程。这既让文件轮转可行（Windows 上多进程轮转同一文件会因文件锁失败），也构成一个必须写进文档的前提条件。
3. **同步路由跑在线程池、异步路由跑在事件循环**。`app/storage/db.py` 的 `check_same_thread=False` 注释已经记录了这一点：FastAPI 把同步 handler 派发到 worker 线程。任何"当前请求是谁"的上下文机制必须同时在这两种执行模型下成立。
4. **日志会成为个人信息的第二份副本**。M1 的岗位画像已含自由文本，M2 起含简历内容。脱敏必须是结构性的，不能靠每个调用点的自觉。

## Goals / Non-Goals

**Goals:**

- 日志落盘这件事**零配置即生效**：新部署、新环境不需要先改 `.env` 或计划任务参数才能拿到日志
- 脱敏的正确性可被测试**证伪**——存在一条测试，如果有人把画像对象整体塞进日志，它会失败
- 请求标识的传播机制在同步与异步两条执行路径上都成立，且不依赖调用方手动传参

**Non-Goals（设计层面的边界，范围边界见 proposal.md 的 Non-goals）:**

- 不设计日志的结构化查询与索引，日志是给人读的文本行，不是给程序聚合的数据源
- 不设计多进程/多实例下的日志合并，单进程是当前部署形态的既定前提
- 不设计日志的加密与完整性校验——那是业务审计（`ai-audit-trail-and-outbound-gate` 的 hash-chain）的职责，运行日志明确定位为可轮转、可过期、不作为举证依据

## Decisions

### 决策 1：在应用内用一处 `dictConfig` 统一配置，而不是靠计划任务重定向或 `--log-config`

**选择**：进程启动时（`app/main.py` 导入期，早于 `create_app`）调用一次日志初始化，用 `logging.config.dictConfig` 同时配置根 logger、应用 logger 与 uvicorn 的三个 logger（`uvicorn`、`uvicorn.error`、`uvicorn.access`）。

**为什么不是计划任务重定向**：约束 1 已经堵死了——计划任务的 action 没有 shell。要重定向就得把 `-Execute` 换成 `cmd.exe /c "uvicorn … > log 2>&1"`，这会让计划任务监控的是 `cmd.exe` 的退出码而不是 uvicorn 的，"失败重启 3 次"的判定跟着失真。而且重定向出来的单文件无限增长，不满足容量有界。

**为什么不是 `uvicorn --log-config`**：它只接管 uvicorn 自己的 logger，应用代码的 logger（如 `app.storage.idempotency`）还要另配一份。两套配置分处两地，漂移只是时间问题——而这次事故要救的恰恰是应用侧那条 `logger.error`。

### 决策 2：按天轮转 + 保留份数，用同一个参数同时锁住容量上界与留存期

**选择**：`TimedRotatingFileHandler`，按天切分，`backupCount = 留存天数`（默认 30）。这样"保留份数"与"留存期"是同一个旋钮的两面，不会出现两个配置互相矛盾（比如留存 90 天但只保留 7 份）。同时设一个单文件大小的兜底上限，防止单日突发日志把磁盘写满。

**为什么不是按大小轮转**：留存期是合规要求（PIPL 存储限期），按大小轮转无法回答"最老的日志是多久以前的"。按天轮转天然给出这个答案。

**代价**：Windows 上轮转时需要重命名当前文件，若有第二个进程持有该文件句柄会失败。这是约束 2 的直接后果，必须写进代码注释与运维文档：**加 `--workers` 之前必须先换轮转方案**。

### 决策 3：`contextvars` 承载请求标识，靠 logging Filter 注入，不改任何调用点

**选择**：ASGI 中间件在请求入口生成标识、写入 `contextvars.ContextVar`，一个 `logging.Filter` 在每条 record 上注入该值，格式串统一带上它。业务代码里所有已有的 `logger.info(...)` 一行都不用改。

**为什么不是 thread-local**：约束 3——异步路由全部跑在同一个事件循环线程上，thread-local 会让并发的异步请求互相覆盖标识，正好违反 spec 的"并发请求互不串扰"。`contextvars` 在 asyncio 任务与 `run_in_executor` 派发的线程两侧都能正确复制上下文。

**为什么不是显式传参**：要改遍所有调用点，且新写的代码会持续遗漏。Filter 注入是一次性的结构改动。

### 决策 4：脱敏的主防线是"不整体记录对象"，Filter 只是兜底

**选择**：两层。

- **主防线（结构性）**：业务对象不得整体进日志。提供一个产出可记录摘要的帮助函数，只输出显式白名单内的非内容字段（如 `job_id`、`round_count`、字段数量、内容长度）。白名单之外一律不输出——对应 spec 的"未声明即受控"。
- **兜底（探测性）**：一个 `logging.Filter` 扫描最终 record，命中已知的高危键名（画像内容、简历文本等）时做替换并额外记一条告警。

**为什么两层**：Filter 单独用不可靠——正则永远追不上业务字段的增长速度，且它只能看到已经格式化的字符串，嵌套结构容易漏。但只有主防线也不够：异常堆栈里的局部变量、第三方库的调试输出都不经过我们的帮助函数。主防线负责正确性，兜底负责"当有人绕过主防线时至少留下痕迹"。

**测试形态**：断言"把一个含受控字段的对象交给日志系统后，最终文件里搜不到那段明文"。这条测试就是主防线被绕过时的报警器。

### 决策 5：日志写入失败不崩溃，但要在健康检查里暴露

**选择**：启动时探测日志目录可写；不可写时，服务照常提供业务功能，但把"日志子系统降级"这个事实写进健康检查端点的返回内容。

**为什么不是"失败即退出"**：日志是排障设施，不是业务依赖。因为日志目录权限问题导致整个招聘助手不可用，是拿更大的故障换更小的故障。

**为什么必须暴露在健康检查里**：spec 明确要求"MUST NOT 静默降级为什么都不记录"。而在一个没有控制台、日志本身又坏了的进程里，健康检查端点是唯一还能对外说话的通道。

### 决策 6：日志目录默认值写在代码里，`.env` 只做可选覆盖

**选择**：默认 `<AppDir>/logs/`，不需要任何配置即可工作。`.env` 可覆盖路径、级别与留存天数。

**为什么**：`.51` 的 `.env` 是服务器上独立维护的生产凭据文件，不随代码同步（见 `sync-to-server.sh` 的白名单说明）。如果日志功能依赖 `.env` 新增字段，那么"推代码"与"改 .env"就成了两个必须同时做对的步骤，漏一个就静默地没有日志——正是这次要根治的失败模式。默认值兜底后，部署忘了改 `.env` 的后果只是用了默认路径，而不是回到零日志。

## Risks / Trade-offs

- **将来给 uvicorn 加 `--workers` 会打破按天轮转**（Windows 文件锁）→ 在代码注释、`05-发布运行手册.md` 与运维文档三处写明前提；轮转失败本身会触发决策 5 的降级暴露，不会静默
- **兜底 Filter 给人虚假安全感**，可能让人以为"随便打日志也没事"→ 主防线的测试断言是硬门槛，Filter 命中时额外记告警，使绕过行为可见而不是被悄悄修正
- **`contextvars` 在自行创建的裸线程中不自动继承**（`threading.Thread` 手动启动的场景）→ 当前代码没有这种用法；LangGraph 内部线程池由 `concurrent.futures` 派发，会复制上下文。若将来引入裸线程，日志会缺标识而不会错标识，属可接受的降级
- **日志目录写满磁盘** → 留存期与保留份数双重上界；`.51` 当前剩余约 70GB，按当前流量（15 个会话/8 天）风险极低，但上界仍必须存在
- **新增中间件改变响应头** → 现有 `tests/test_web_api.py` 若断言了响应头集合可能需要适配；子路径挂载测试（`test_app_works_when_mounted_at_arbitrary_subpath`）必须继续通过，中间件不得硬编码路径前缀（部署约束 1）
- **日志目录若被误加进同步白名单，会把生产日志反向拉回开发机** → 属合规事件（未授权的个人信息转移）；任务里包含一条显式验证，不假定"现在没有就永远没有"

## Migration Plan

1. 本地实现并跑通全量测试，含新增的落盘、轮转、串联、脱敏四类测试
2. 推 CI（Windows runner）验证——轮转与文件锁的平台差异只有真实 Windows 才测得出，这正是 SQLite 事务冲突那次的教训
3. `.51` 发版：同步代码 → 确认 `logs/` 目录由 SYSTEM 账户可写 → 重启计划任务 → 验证日志文件确实产生且内容非空。**该步是生产发版决定，按 CLAUDE.md 决策代理表不可代，须 Shao Peishen 拍板**
4. 回滚：日志功能是纯增量，回滚等于回退代码同步并重启计划任务；无数据迁移、无 Schema 变更，回滚后系统退回当前的"无日志"状态，不会损坏任何已有数据

## Open Questions

- **留存天数的最终取值**（默认拟定 30 天）需要与卓品智能内部的日志留存口径对齐。这不影响 spec、方案与任务拆解——它是一个配置项的默认值，改动成本是一行——因此不阻塞实现。
