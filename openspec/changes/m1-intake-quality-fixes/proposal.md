## Why

3 位业务经理真实试跑（2026-08-13 / 08-18）暴露了一批采集质量缺陷，`docs/m1-demo-pilot-feedback.md`「反馈 2、3 的调查」已用服务器 `data/demo.db` 的 `conversation` / `job_profile` 逐轮快照核对过，不是主观体感：

- **用户说"我不知道、你有什么建议"时，系统整轮空转。** 软件岗（`19b6ec6d`）第 4 轮用户回"这些我不太了解，你有什么建议"，AI 只回了一句"您可以按建议补充岗位要求……我来帮您整理"；供应链岗（`a478499c`）第 5 轮用户反问"一般材料是什么，你都不知道吗"，AI 只回了一句道歉并把同一个开放问题原样抛回。两轮的 `job_profile.profile_json` 长度与上一版**逐字节相同**（217→217、143→143），确认零产出。5 轮预算里白烧掉 1 轮，直接导致 `toolchain` / `soft_skill_keywords` / `functional_safety` 等字段最终进了 `unspecified_fields`，对应上经理"工具链要求缺失、软技能未提、加分项偏单薄"的抱怨。
- **追问只能靠打字自由回答。** 经理原话："我回复你推荐问题时的选择内容和方式有点不顺，复制粘贴编辑有点麻烦，最好直接选择项加，文字描述"。与上一条是同一个问题的两面——系统不给可选项，用户就只能自己编答案，编不出来就只能说"你有什么建议"。
- **未答的子问题被换措辞重问，用户体感是"问过了怎么又问"。** 采购岗（`2494103e`）第 3 轮把"IATF 16949 / ISO 26262"打包成一个问题串，用户只答了前者；第 4 轮系统把 ISO 26262 拆出来重问，措辞不同、话题相同。2026-08-11 上线的逐字重复检测（`_repeats_earlier_assistant_turn`）按定义抓不到——原文本来就不一样。
- **`unspecified_fields` 既不可靠、又看不见。** 它当前完全由 LLM 自由生成（`app/agents/intake_agent.py:233` 直接透传 `parsed.unspecified_fields`），不是系统按画像字段推导的：供应链岗强制收尾时该字段为**空数组**（漏报），软件岗却把用户已经答过的 `functional_safety`、`sop_projects` 也列了进去（虚报）。前端还只把它渲染成对话流里的一行英文 snake_case 小字（`app/web/static/index.html:49-52`）。两位经理都点了确认，事后才在 JD 里发现同样的缺口。

- **"没有编造"这个结论至今没有被真正验证过。** 三位业务经理在编造检查一项上都答了"无编造"，但核对表单原件后发现：反馈 2、3 两位贴进第 2 题的是**生成后的 JD 文本截图**，不是表单明确要求的"确认画像"那一页截图（`docs/m1-demo-manager-guide.md:27` 原话："把'确认画像'那一页**整页截图**"）；反馈 1 走的是更早的自由记录方式，没有留下经理看的是哪一页的任何记录。也就是说，表单设计想要的"对着结构化字段表逐条圈出编造内容"这个动作，**一次都没有针对正确对象做过**——连续成文的 JD 文案本来就比一份字段表难挑错，字段级的编造混在 JD 里几乎看不出来。`deepseek-v4-pro` 实测 3 次里有 1 次凭空抽出输入完全没提到的 MCU 型号与工具链（ARM Cortex-M / Infineon TriCore / Keil / IAR），现已换成 flash，但 **flash 在真实使用中的编造率至今是未知数**。**这不是"验证通过"，是"没验证"。** 画像里多出业务经理没说过的硬性要求 → 寻源方向偏 → 后面全白做，且很难被发现——这一项比字段准确率更要紧。

这些缺陷都发生在整条招聘链路的**输入端**——画像质量决定后面寻源、匹配、面试全部环节的方向，且缺陷已被三个独立样本中的两到三个同时命中，不是偶发。

## What Changes

- **追问改为"结构化问题 + 可选项"。** 单个追问从裸字符串变成带稳定 `question_id`、`field`、`options[]`、`allow_free_text` 的结构化对象；Web 前端把 `options` 渲染成可点选控件（单选/多选 + "其他"自由输入），点选结果直接构成回复文本，不再要求用户复制粘贴编辑。
- **模糊回答兜底：必须给档位，不许回空话。** 系统确定性地识别"不知道/你决定/随便/你有什么建议"以及"反问系统"这类模糊回复，命中时该轮问题 MUST 携带该领域 2-3 个具体可选档位（例如功能安全等级列 `ASIL-B` / `ASIL-D` / `无要求`），档位优先取自 `app/agents/ecu_knowledge.py` 的领域选项库。**AI 给的是候选项，不是结论**——用户没有明确选定前，不得把任何猜测值写进 `profile_patch`。
- **零产出轮不消耗追问预算（有硬上限）。** `MAX_ROUNDS=5` 改为计"有产出的追问轮"：既没提取到任何新字段、也没问出新问题的轮次不计入预算，同时设 `MAX_TOTAL_ROUNDS` 硬上限防止无限循环。
- **未答子问题的诚实重问。** 系统按 `question_id` 追踪"已问但未答"的子问题；重问时 MUST 在措辞上明确标注"这个你刚才没答"，并且 MUST NOT 与新问题混编成看起来像新问题的一句话。同一个 `question_id` 重问次数有上限，超限即计入未指定字段而不是继续追。
- **`unspecified_fields` 由系统推导，不再信 LLM。** 改为在强制收尾时按 `JobProfile` 的字段表与已累积画像做确定性差集；LLM 输出的同名字段只作为参考信号，不再直接透传。
- **确认前的显著缺口警示。** 未指定字段以**中文字段名 + 视觉显著警示块**呈现在"确认画像"按钮上方，并要求用户在"回去补答"与"知道有缺口，仍然确认"之间做一次显式选择——不再是对话流里一行可以被划过去的小字。
- **逐轮时序留痕（最小范围）。** 把 `LLMGateway` 已经算出来但被 `NoopAuditHook` 丢弃的 `latency_ms`，连同该轮的开始/结束时间戳，落到 `job_profile` 行上，使"单轮 LLM 延迟"与"用户思考时长"可以被分开度量。**明确不建 `analysis_run` 表、不做 hash-chain**——那属于 `ai-audit-trail-and-outbound-gate`，本变更这两列在该变更落地后由 `analysis_run` 取代。
- **字段溯源：把编造变成可数的数字（本批只观测、不拦截）。** 模型写进 `profile_patch` 的每个字段 MUST 附带来源——一段**逐字取自用户某轮原话**的引用片段与该轮序号；系统做确定性校验（引用片段必须是被引用那轮用户文本的子串，不调模型、可单测）。校验不通过的字段标记为未溯源并计数，连同该轮 API 实际返回的模型标识一并落库，使**编造率可以按模型版本被统计出来**。**本批不拦截**——未溯源字段仍然写进画像，只计数：flash 的真实编造率还是未知数，在拿到分布之前定拦截阈值是凭想象。拦截策略等本批上线后的真实数据出来再单独定。

### 三项调查的结论（据此定的范围）

1. **轮次计数没有 off-by-one。** `run_intake_turn` 收到的 `round_count` 是本轮**之前**的 `job_profile` 行数，第 6 条用户消息进来时 `round_count=5` 命中 `>= MAX_ROUNDS` 强制收尾，且该轮用户的回答仍会被吸收进画像。三段真实会话都恰好是 6 条用户消息 / 6 个画像版本，与经理填的"追问轮数 6"完全吻合——**语义是"最多 5 轮追问 + 第 6 轮吸收后收尾"，不是少算或多算一轮**。真正的缺陷在旁边：零产出轮（上文两处）照样占满一格预算，非用人需求的消息也会写出一个 `job_profile` 行、同样占预算。因此本变更纳入"零产出轮不消耗预算"，不纳入任何计数器改名或阈值调整。
2. **姚祖怡的"不理解你想问的问题"定位到了具体轮次。** 是 `a478499c` 的第 5 轮：系统前一轮问"该岗位采购的'办公系统'具体指哪些？……"，用户回"一般材料是什么，你都不知道吗"（用户在反问系统一个本该由系统的领域知识回答的问题），系统回"抱歉，您能具体说明一下该岗位采购的'一般材料'指哪些类别吗？"——道歉 + 原样抛回，零字段产出。**这与"你有什么建议"是同一个失败类**（用户把球踢回来、系统再踢回去），因此归入同一条兜底要求，不单列。
3. **可观测性缺口是真的，但比想象的小，且部分已被别的变更覆盖。** `job_profile.created_at` 已经逐版本记录了轮次**结束**时间（软件岗 6 轮跨 6 分 53 秒，逐轮间隔 50/51/85/128/99 秒），但这些间隔混着用户打字思考时间，无法回答"单轮等待感受"对应的真实 LLM 延迟；而 `latency_ms` 其实已经在 `app/llm/gateway.py:176-178` 算出来了，只是被 `NoopAuditHook` 丢掉。**决定：以最小形态纳入本批**——理由是 P0/P1 的修复必须能被验证（"兜底选项是否真的减少了空转轮、有没有把延迟拖爆"），而完整的 `analysis_run` 留痕在 `ai-audit-trail-and-outbound-gate` 里、尚未实现，等它会让本批的效果无法度量。

## Capabilities

### New Capabilities

- `intake-guided-options`: 引导式可选项追问——追问以结构化问题 + 可选项形式下发并可点选作答；用户表达"不知道/你决定/你有什么建议"或反问系统时，系统必须给出该领域 2-3 个具体档位而不是空话回抛；AI 提供的档位只作候选，未经用户明确选定不得写入画像；零产出轮不消耗追问预算（带硬上限）
- `intake-question-tracking`: 追问的已问/已答追踪——每个子问题带稳定标识，系统按标识判定"已问未答"，重问时必须显式标注为重问而非伪装成新问题，同一子问题重问次数超限即转为未指定字段
- `intake-completeness-warning`: 画像完整性警示——未指定字段由系统按画像字段表确定性推导（不再透传 LLM 输出），以中文字段名与视觉显著的警示块呈现在确认动作之前，并要求用户在"回去补答"与"知情确认"之间显式选择
- `intake-turn-observability`: 逐轮时序留痕（最小范围）——每轮记录 LLM 调用延迟与轮次起止时间戳，使 LLM 延迟与用户思考时长可分开度量；不含 `analysis_run` / hash-chain 等完整审计设施
- `intake-field-grounding`: 画像字段的来源可追溯与编造度量——写进画像的每个字段都必须携带逐字取自用户原话的来源引用，系统按确定性规则校验并把未通过校验的字段与该轮 API 实际返回的模型标识一并留痕，使编造率可按模型版本统计；本批只度量、不拦截

## Non-goals（不做什么）

- **不做企微通道**——结构化问题与选项的下发格式要为企微卡片留出兼容位，但本变更只实现 Web 通道的渲染
- **不做 Postgres 迁移**——继续用 SQLite，新增列走现有 `init_schema` 路径
- **不做审计留痕落表**——不建 `analysis_run` / `criterion_score`、不做 hash-chain、不接 `AuditRecorder`，那些是 `ai-audit-trail-and-outbound-gate` 的范围
- **不换 LLM 供应商、不换模型、不调 temperature**
- **不改追问上限的数值**（`MAX_ROUNDS` 仍为 5）——本变更改的是"什么算一轮"，不是"允许几轮"
- **不引入前端框架**——选项控件用原生 DOM 实现，`app/web/static/index.html` 保持单文件无构建
- **不做画像字段的人工直接编辑**（在确认页上手改字段值）——警示块只引导用户回到对话里补答，编辑态属于后续范围
- **不做重复问题的语义相似度检测**——按 `question_id` 做确定性追踪即可覆盖本次暴露的场景，语义去重成本高且不可解释
- **不拦截未溯源字段**——本批只把编造变成可数的数字。拦截阈值与降级策略必须建立在真实编造率分布上，而那个数据要等本批上线后才会有
- **不做人工标注式的编造评测**——不建标注流程、不引入第二个模型当判官；本批的编造信号必须是确定性、可复算的

## 合规影响说明

- **本变更不处理候选人个人信息。** 采集对象仍是岗位需求；新增的时序字段记录的是业务经理与系统的交互时间，属人力资源管理必需，依 PIPL 第 13 条第（二）项处理。
- **《AI 生成合成内容标识办法》（2025-09-01 施行）**：系统给出的档位选项是 AI 生成内容，UI 上 MUST 标明是"建议选项"而非既定要求。
- **AI 不得代替业务经理做决定**：兜底档位只能作为候选项呈现，用户未明确选定前不得进入 `profile_patch`——这是"AI 只做推荐不做决定"红线在采集端的对应约束，且必须有测试覆盖。
- **可解释性（铁律 5「锁不住版本至少要记得住版本」在采集端的落地）**：字段来源引用与该轮 API 实际返回的模型标识（`response.model`，不是配置里写的别名）一并落库，将来才回答得了"这条硬性要求是哪个模型版本、依据业务经理哪句原话写进画像的"。
- 未指定字段的警示块与用户的"知情确认"选择需要落痕，以便回答"这份画像确认时业务经理是否知道有缺口"。
