## Why

业务经理提用人需求时通常只有一句话（"要个做嵌入式开发的，能写驱动"），HR 翻译不准，导致寻源方向从第一步就偏了。返工成本在后面每个环节被放大：JD 写错 → 简历投递不对口 → 筛选白做 → 面试官时间浪费。

M1 是整个招聘智能体的第一块，也是风险最低的一块——它不接触候选人个人信息，却能完整验证系统的主链路形态（Agent 多轮对话 → 结构化产出 → 人工断点 → 冻结）。先把这条链路跑通，后面 M2、M3 才有可复用的地基。

## What Changes

- 新增对话式需求采集：业务经理在企业微信里用自然语言提需求，Agent 基于 ECU 领域知识库多轮追问，补全模糊项
- 新增结构化《岗位画像》产出：核心技术栈（必会/加分）、ECU 特化字段、项目经验要求、软技能关键词
- 新增硬门槛规则草案：Agent 从画像中提取可自动判定的过滤条件（学历、年限、必备技能），供 M2 使用
- 新增人工确认断点：画像草案通过企微卡片推给业务经理，确认后冻结，未确认则流程挂起（可跨天）
- 新增 JD 生成：基于冻结画像生成招聘文案，**带 AI 生成标识**
- 新增流程编排骨架：LangGraph + Postgres checkpointer，`interrupt()` 落库挂起、企微回调唤醒。这是后续 M2/M3 共用的地基

## Capabilities

### New Capabilities

- `job-profile-intake`: 对话式用人需求采集与多轮追问，产出结构化岗位画像草案与硬门槛规则草案
- `job-profile-approval`: 岗位画像的人工确认断点与冻结，含挂起、唤醒、修改、超时提醒
- `job-description`: 基于冻结画像生成招聘文案，含 AI 生成内容标识

### Modified Capabilities

（无，本项目首个变更）

## Non-goals（不做什么）

- **不做简历相关的任何功能**——解析、评分、排序全部属于 M2
- **不做多平台 JD 适配**（Boss直聘/猎聘/智联的不同文案风格）——一期只产出一份通用文案，HR 自行调整。渠道对接本身已确定推迟到二期
- **不做 JD 自动发布**——没有渠道 API，一期靠 HR 手工发
- **不做岗位画像的版本对比与复用推荐**（"上次招这个岗用的是什么画像"）——等有了历史数据再说
- **不做审批链**（多级审批、会签）——一期只有业务经理单点确认
- **不引入前端框架的复杂度**——企微卡片交互为主，Web 端只做画像查看

## 合规影响说明

- **本变更不处理候选人个人信息。** 采集对象是岗位需求，不涉及任何求职者数据。
- 处理的个人信息仅限**内部员工标识**：业务经理的企微 userid、姓名、部门，用于流程流转与操作留痕。属于人力资源管理必需，依 PIPL 第 13 条第（二）项处理。
- **AI 生成内容标识**：生成的 JD 属于《人工智能生成合成内容标识办法》（2025-09-01 施行）规制范围，必须带标识。本变更包含该实现。
- **审计留痕**：画像生成与确认的全过程（模型版本、prompt 版本、输入、输出、确认人、确认时间）落库，为后续 M2/M3 的合规审计建立统一机制。
- **PIA 前置**：M2 处理候选人简历前必须完成个人信息保护影响评估。本变更需搭好审计表结构以支撑 PIA，但 PIA 报告本身不在此变更范围。

## Impact

**新增代码**
- LangGraph 编排骨架与 Postgres checkpointer 接入
- LLM 网关（多供应商、模型版本显式锁定、`temperature=0`）
- 企业微信自建应用：`template_card` 消息推送 + HTTPS 回调接收
- 需求解析 Agent（纯函数）
- 数据表：`job`、`hard_requirement`、`analysis_run`、`human_review`、checkpoint 表

**新增依赖**
- `langgraph >= 1.0.10`（低于此版本存在 GHSA-g48c-2wqr-h844 checkpoint 反序列化问题）
- `langgraph-checkpoint-postgres`、`psycopg`、`pydantic`、`fastapi`

**外部系统**
- 企业微信自建应用需申请，回调地址需公网 HTTPS 可达
- LLM 供应商账号（W1 实测后定型，至少接两家以便切换）

**风险面**
- LangGraph 恢复时节点从头整个重跑 → 所有有副作用的动作必须独占节点并带幂等键。这条约束在本变更中首次落地，后续所有变更沿用。
