# 准入名单的填写与变更

## 改名单不需要改代码

`whitelist.yaml` 是本服务准入判定的**唯一**数据来源。加载器每次判定都重新读它，
因此改完**重启即生效，不重启也已生效**。⛔ 代码里没有任何硬编码的默认名单，
改 `.py` 不会、也不该改变谁能进。

## 字段只有三个

| 字段 | 含义 |
|---|---|
| `userid` | 企业微信内部用户标识 |
| `name` | 中文姓名（用于日志与人工核对） |
| `role` | 角色说明（用于回答"这个人为什么在名单里"） |

⛔ **不要加第四个字段**，尤其不要加手机号、邮箱、身份证号。
加载器是**白名单式**校验：条目的键集合不等于这三个，**整条丢弃**并记 ERROR ——
后果是这个人进不来，不是"多余字段被忽略"。这是刻意的：合规要求由加载器执行，不靠人眼。

## 追加一名成员

1. 在 `members` 下追加一条，三个字段齐全，`userid` 非空。
2. 提交。⛔ 不改任何 `.py`。
3. 重启服务（或什么都不做——下一条消息进来时就会读到新名单）。

⚠️ 追加成员本身是一次**范围扩大**：名单外的人只是收不到任务队列条目，
名单内的人可以往值守任务队列里写行。D2 的判据是"默认从紧"——
确有材料提交职责时按名录单条追加并留痕，⛔ 不要把群成员整批放进来。

## userid 为空怎么办

出厂配置的两条 `userid` 都是空串，因为写这份配置时**真实企微 userid 尚未取得**。
空 userid 的条目会被丢弃，所以出厂态是**谁都不准入**。
拿到真实 userid 后填进去即可；⛔ 不要填假值占位——假值让闸门看起来配好了、
实际谁都进不来，而这个失败不可见（没人会收到礼貌回复来提示你名单是坏的）。

## ⚠️ 失败面：改坏这个文件 = 拒绝所有人，唯一提示是 ERROR 日志

上面说"改完不重启也已生效"——反过来同样成立：**改坏了也是立刻生效**。
加载器是 fail-closed 的，任何一种失败都折成"空名单"，后果统一是**谁都进不来**：
名单内的人发消息不再进任务队列，而机器人**不会**报错、**不会**回一句"名单坏了"。
⛔ 唯一的提示是本服务 `tools.liaison.whitelist` 这个 logger 的 ERROR 日志。
改完名单请去看一眼日志，⛔ 不要以为"没报错就是好了"。

| 失败面 | 典型现场 | 日志里会说什么 |
|---|---|---|
| YAML 语法写坏 | 少个引号、缩进对不齐、粘贴时串行 | 解析失败 + 行列号（⛔ 不回显源文本） |
| **重复键** | 在文件末尾**再追加一段** `members:`，而不是并进原有列表 | 出现重复键 + 键名 + 行列号 |
| **存成非 UTF-8** | Windows 记事本/Excel 另存时编码选了 GBK/ANSI | 不是 UTF-8 编码 + 出错字节偏移量 |
| 存盘竞态 | 编辑器写到一半、正好有消息进来读到半份文件 | 按上面某一类报（下一条消息就会重新读，自愈） |
| 字段不合规 | 加了第四个字段、`userid` 留空 | 第 N 条整条丢弃 + 字段名（⛔ 不写字段值） |
| 全部条目都被丢弃 | 出厂态（两条 `userid` 都是空串） | 零条有效条目，全部发送人判为未命中 |

⚠️ **重复键这一条最值得记住**：PyYAML 的原生行为是**静默取后者**——
"追加一段 `members:`"会变成"用新那段**替换整份名单**"，零日志、闸门看起来健康、
人却换了一批。本服务专门把它改成了拒绝，⛔ 不要绕过它（比如把两段合并成
一段之外的任何"变通"）。**追加成员的正确做法只有一个：并进已有的那个 `members` 列表。**

⚠️ **同一份坏内容不会反复刷屏**：ERROR 按"名单文件内容"去重，
同一份内容连续失败只记**一组**，内容一变会重新记一组（技术债 TD-15）。
所以**日志安静不等于问题好了**——它可能只是还是那份坏内容。
组尾那行 `以上准入名单失败按文件内容去重…` 就是在提醒这件事。
去重只作用在写日志这一步：判定路径每次仍然重新读文件、重新解析，⛔ 名单本身从不缓存。
